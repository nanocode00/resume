# HCI Stock Information Service — 리포트 기반 주식정보 탐색 웹 서비스

> **검토 상태(2026-10-28):** GitHub 원본 코드·개인 작성 커밋·2025년 팀 발표 자료·18명 설문 원본·통계표를 대조해 **경험 복원 v1**을 작성. 개인 기여와 팀 성과를 별도로 서술하며, 실제 서비스 재실행·장기 운영·개별 역할 분담은 전부 증명된 것으로 간주하지 않는다. 세부 근거는 [HCI 조사 원장](hci-stock-service-evidence-ledger.md) 참고.

**2025년 가을 지능 HCI 3인 팀 프로젝트**에서 분산된 국내 증권사 리포트 정보를 종목·기관·애널리스트·투자의견 기준으로 조회하기 위한 **SQLite/SQLAlchemy 정규화 DB와 기본 검색 쿼리**를 직접 구현했다. 팀은 이를 바탕으로 웹 서비스를 만들고 기존 정보 사이트와 비교하는 18명 대상 사용자 평가를 진행했다.

- **개인 구현의 강한 증거:** [본인 Git 커밋 2660f755](https://github.com/nanocode00/hci/commit/2660f755f403fab6f6b2381541cd699d24c8f02d), 2025-11-24. 초기 **db.py**, **query.py** 신규 추가; 리포트 자료·쿼리 출력물도 포함. 이 한 커밋의 총 추가량은 소스 코드의 직접 작성 줄 수와 동일하지 않다.
- **팀 결과의 강한 증거:** 원본 **지능HCI_2조_1차발표.pptx**, **지능HCI_2조_최종발표.pptx**, **hci_interview.csv**, **hci_interview_t-test.pdf**. 발표와 데이터는 **팀 활동의 근거**이고 설문 설계·모집·분석을 모두 본인이 주도했다는 개인 귀속 근거는 아니다.
- **원본 프로젝트:** [nanocode00/hci](https://github.com/nanocode00/hci), 공개 main, 2025-11~12월의 FastAPI/Jinja2/SQLite 코드가 보존되어 있다. 제3자 템플릿·팀원 커밋을 개인 단독 구현으로 주장하지 않는다.

## 프로젝트 배경 및 구현 범위

### 상황·목표

기존 증권 리서치 사이트에는 종목별 리포트가 흩어져 있고, 비전문 사용자가 여러 기업·증권사의 정보를 한 화면에서 비교하기 어렵다는 문제를 팀이 제기했다. 2025년 10월 1차 발표에서는 **통합 검색, 단계적 정보 제시, 통계 시각화, 사용자 피드백**을 기획했다. 이는 **목표/설계**이지 당시 모두 완성된 구현이 아니다.

최종 발표(2025년 12월)에서 팀은 **리포트 PDF 확보·요약, FinanceDataReader 주가 정보, 웹 UI, Render 배포, 사용자 비교 평가**를 소개했다. 남은 저장소 코드에는 FastAPI/Jinja2 웹 라우트, SQLAlchemy/SQLite, 한경 컨센서스 데이터 수집기, FinanceDataReader 주가 갱신, PDF 처리 파이프라인의 일부가 존재한다. 단 **Gemini API를 호출하는 리뷰 생성 파일은 현재 main에 남아 있지 않아 요약 기능의 완전 재현은 검증되지 않았다.**

### 개인 구현의 확인 범위

본인 명의의 [Git 커밋](https://github.com/nanocode00/hci/commit/2660f755f403fab6f6b2381541cd699d24c8f02d)에 다음이 신규 추가되었다.

| 파일·영역 | 직접 확인한 구현 |
|---|---|
| **db.py — 스키마** | SQLAlchemy 선언형 모델 **Stock / Broker / Author / Rating / Report** 5개, 외래키 및 관계 설정. 중복되는 종목·기관·애널리스트와 개별 리포트 레코드를 구분 |
| **db.py — 적재** | SQLite 엔진·세션, 초기 투자의견 코드, CSV 컬럼 파싱, 문자열·숫자 변환 및 Buy/Sell/Hold/None 정규화, 종목/증권사/애널리스트 캐시와 조회를 통한 중복 레코드 방지 |
| **query.py — 조회** | 전체 리포트 최신순 조회, 종목명/증권사명/애널리스트명 부분 일치 검색, 투자의견 코드 검색 및 출력 포맷 |
| **검증 흔적** | 해당 커밋에 조회 예시 결과 텍스트가 함께 존재하여 **데이터 조회를 실행한 흔적**이 있다. 정식 자동화 테스트나 성능 벤치마크를 뜻하지 않는다 |

설계는 엔터티를 분리해 **3정규형을 지향하는 관계형 구조**다. 다만 의존성 전체에 대한 별도 형식적 검증은 없으므로 **엄밀한 3NF 증명 완료**로 확대하지 않는다.

그 외 저장소의 웹 UI/배포/스크래퍼/주가 수집/요약 연결은 **팀 전체 코드**로 분류한다. 현재 main에서 확인되는 57개 일반 커밋의 Git author 표기는 **nanocode 1개, heo 56개**다. 이 집계는 공개 main 이력의 표기에 한정하며, 로컬 비커밋 코드나 다른 팀원의 계정 공유·실제 참여를 부정하는 근거가 아니다. 본인 이름으로 올라오지 않은 기능을 개인 기여로 확대하지 않는다.

## 경험 1 — 데이터 구조와 CSV 적재 설계

### 상황
증권사 리포트 데이터에는 기업 코드·이름, 작성 기관·분석가, 투자의견·작성일·목표가 등 반복 항목과 리포트별 고유 속성이 함께 있었다.

### 문제
리포트를 단일 비정형 목록으로만 관리하면 기업별 검색과 기관별 비교에 사용될 동일 속성이 반복되고, 별도로 관리해야 할 리포트 개별 정보를 구별하기 어렵다. **이는 당시 사용 목적과 코드 구조에서 추출한 기술 과제**이며, 실제 중복 장애가 발생했다는 증거는 없다.

### 판단
반복 사용되는 **종목, 증권사, 애널리스트, 투자의견**을 개별 테이블로 분리하고, 보고서 자체는 **Report**에 보관해 외래키로 연결하는 구조를 택했다. CSV 입력값의 숫자·문자열·투자의견 표기를 정규화하는 처리가 필요하다고 보았다.

### 조치
**Stock / Broker / Author / Rating / Report** 모델을 SQLAlchemy로 정의했다. SQLite 세션과 테이블 초기화를 구현했고, CSV의 작성일·종목코드·이름·목표가·가격·평가의견·작성기관·애널리스트·첨부 URL을 파싱했다. 동일 종목·기관·작성자가 중복 삽입되지 않도록 세션 쿼리와 메모리 캐시를 함께 활용했다. Buy/Sell/Hold/None의 평가의견 코드로 다양한 표기 값을 통합했다.

### 결과
2025-11-24 개인 커밋에서 **관계형 스키마와 CSV 적재 코드가 실제로 제출된 것**을 확인했다. 이는 이후 검색 기능을 위한 데이터 기반을 만든 구현 사례다. **총 적재 건수, 누락률, 처리 시간, DB 운영 안정성의 계측값은 확인되지 않았다.**

## 경험 2 — 사용자 탐색을 위한 기본 검색 쿼리

### 상황
팀이 지향한 서비스는 사용자가 개별 회사뿐 아니라 증권사나 분석가·평가의견별로도 리포트를 찾아보는 흐름이었다.

### 문제
리포트에 여러 차원의 연관 정보가 있으므로 한 종류의 검색만으로는 비교 요구를 충족하기 어렵다. UI 검색과 데이터 접근 경계를 명확히 할 필요가 있었다. **해당 문제의 실제 사용자 불편 발생 및 팀 내 독자적인 요구사항 결정자는 미확정**이다.

### 판단
SQLAlchemy 관계 및 조인 기반 조회를 사용해 **리포트라는 동일 데이터**를 종목·증권사·애널리스트·투자의견 기준으로 검색하고, 작성일 최신순으로 정렬하는 기본 접근 방식을 만들었다.

### 조치
**query.py**에 전체 최신순 출력과 **search_by_stock_name / search_by_broker / search_by_author / search_by_rating** 함수를 구현했다. 연관 객체의 종목명·목표가·평가의견·증권사·작성자·원문 URL을 일정한 출력 포맷으로 정리했다.

### 결과
개인 커밋의 **query.py 108줄**과 함께 저장된 일부 예시 출력 파일에서 검색 결과가 생성된 흔적을 확인했다. 다만 **이 CLI 검색 코드가 최종 웹 UI에 그대로 호출되었다고는 단정할 수 없다.** 최종 FastAPI에서는 별도 검색 라우트가 **Report + Stock + Broker + Author**를 조회하는 팀 코드를 사용한다. 검색 성능 개선이나 UI 만족도 증가를 **개인 검색 쿼리의 독립 효과**로 귀속하지 않는다.

## 경험 3 — 팀의 사용자 비교 평가 (개인 단독 성과 아님)

### 상황
기존 한경 컨센서스(A) 대비 팀이 만든 주식정보 서비스(B)가 사용자에게 더 이해하기 쉽고 탐색하기 편한지 비교 평가할 필요가 있었다.

### 문제
기능 구현이나 정성적 인상만으로는 사용자 경험 개선 여부를 확인할 수 없었다.

### 판단
팀은 같은 응답자가 **A/B 사이트를 모두 평가**하는 설문을 진행하고, **정보 구조 직관성·정보 탐색 자연스러움·전반적 만족도**를 5점 척도로 비교했다. 당시 통계 보고에는 대응표본 t-검정이 사용되었다.

### 조치
2025-12-09와 12-11 수집된 **18명 설문 원본 CSV**, 팀 최종 발표 슬라이드, **hci_interview_t-test.pdf**를 대조했다. **본 문서의 숫자 재계산은 2026년 이력서 복원을 위한 사후 검증**이며, 당시 본인이 설문을 직접 운영·분석했다는 실적으로 소급하지 않는다.

### 결과

| 평가 항목 | A 기존 사이트 평균 | B 팀 서비스 평균 | B - A | 원본 대응 t-검정 |
|---|---:|---:|---:|---|
| 정보 구조 직관성 | 2.72 | **4.28** | +1.56 | t(17)=-4.93, p<0.001 |
| 정보 탐색 자연스러움 | 2.78 | **4.44** | +1.67 | t(17)=-5.95, p<0.001 |
| 전반적 만족도 | 2.44 | **4.44** | +2.00 | t(17)=-6.86, p<0.001 |

- 향후 사용 의향 Yes: **A 5/18명(27.8%) → B 17/18명(94.4%)**. 각 사이트별 질문의 원본 응답을 재집계한 결과다.
- B 서비스 통계/분석 정보가 **매우 유용 12명, 어느 정도 유용 6명**(총 18명)이었다. 최종 발표의 해당 슬라이드 **매우 유용 13명 / 어느 정도 유용 5명**과 **원본 CSV가 불일치**하므로 원본 재집계 **12/6**을 본 문서의 기준값으로 사용하고 차이를 명시한다.
- 대응표본 차이의 정규성 Shapiro-Wilk p값: **직관성 0.019 / 자연스러움 0.276 / 만족도 0.029**. 세 항목 중 **두 항목에서 정규성 가정 위반 신호**가 있으므로 t-검정 결과를 제한 없이 확정적 인과 성과로 제시하지 않는다.
- 소표본(18명), 비무작위·조사 조건 상세 미확인, 다중 비교, 설문 기반 주관 평가 등의 한계가 있다. **실제 정보 탐색 시간 감소, 투자 성과, 장기 사용자 유지율은 측정 근거가 없다.**

이 경험에서 확인되는 것은 **팀의 사용자 비교 평가 결과**다. 설문 설계·응답자 모집·t-검정 수행·발표 담당 등 **개인 역할은 Git 이력·팀 자료만으로 특정할 수 없다.**

## 소스 감사에서 발견한 구현 한계 (2026년 사후 확인)

1. **과거 목표가의 예측 정확도:** 이전 경험 문서에는 이를 확인하는 서비스라는 설명이 있었으나 **보존된 DB에 실현 주가 대비 목표가의 적중/오차 평가를 계산하는 로직은 확인되지 않는다.** 팀 기획과 구현 성과를 분리한다.
2. **요약 파이프라인:** 최종 발표는 PDF에서 Gemini API를 이용한 일반·초급·전문가용 내용 추출을 소개한다. 저장소의 **pipeline.py**는 **get_review.generate_reviews**를 import하지만 해당 **get_review.py**는 현재 보존된 main 트리에 없어 원본 구성만으로 E2E 재현을 입증하지 못한다. 당시 기능이 작동하지 않았다고 단정하는 것도 아니다.
3. **통계 화면:** **statistic.html**과 조회 route가 있으나 **stock_summary view** 생성은 별도 **init_data.py/db.py**에 있고 웹 서버 lifespan에는 직접 호출되지 않는다. **scraper.py**의 현 보존본은 가격·기대수익률을 None으로 넘긴다. 따라서 실제 사용자에게 **Top 30 기대수익률 통계가 유효하게 표시됐는지는 별도 배포 DB·실행 로그 없이는 미확정**이다.
4. **실시간 가격·배포:** 서버 시작 시 FinanceDataReader 주가 갱신 시도 코드는 존재하나, 팀 발표는 **실시간 데이터 업데이트 미지원**을 한계로 인정했다. **서비스를 실시간 시세 제공 시스템으로 기술하지 않는다.** Render 배포 주소는 저장소 README에 있지만 현재 접근·가용성·운영기간은 검증하지 않았다.
5. **인증/템플릿:** sign-in/register 페이지용 템플릿은 있으나 유효한 인증·회원가입 백엔드를 구현했다고 확인할 근거가 없다. 사용한 UI 템플릿 및 타인 원본 자산을 개인 창작물로 귀속하지 않는다.

## 이력서용 선별 문장

## 보여주는 역량과 활용처

- 관계형 모델 설계, 엔터티 분리, Foreign Key 및 ORM 관계, SQLite/SQLAlchemy
- CSV 데이터 전처리·코드값 정규화, 중복 데이터 예방, 조건별 검색 쿼리
- 최종 제품 목표와 데이터 접근 계층의 연결
- 기존 제품 대비 사용자 평가, 검증 통계와 결론의 한계 식별
- 적합 직무: Backend/Database/Software 및 HCI/UX 협업형 프로젝트의 보조 사례

> **다음 확인이 필요한 경우에만:** 개인이 실제 사용자 평가·UI 또는 검색 웹 API를 어느 정도 담당했는지에 대한 당시 팀 자료/직접 회고, 성능·정확도에 관한 운영 로그. 현재 확보한 근거만으로도 **DB·검색 개인 경험은 독립적으로 기술 가능**하며 추가 검증을 완료의 선행 조건으로 두지 않는다.
