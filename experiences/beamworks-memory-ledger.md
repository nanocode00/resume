### 시간·프로젝트의 정확한 진술

- “2026.01 · 4주” 및 구체적 시작/종료일은 회고 기록과 일치하는 범위에서 작성.
- “DealFlow 신규 프로젝트”는 후속 회고에 나온 **이름**이지, 공식 서비스·고객용 제품·상용 영업 CRM이라는 확증은 없다. 타 시스템과의 통합, 자금 흐름 또는 금융 업무 등을 뜻한다고 임의로 해석하지 않는다.
- **Git·Jira·Bitbucket 교육의 존재**와 **그 도구로 실습용/실제 운영 코드를 작성·병합했다는 사실**은 서로 다른 주장이다.

## 3. 5단계 사례의 사실과 해석 분리

| 사례 | 직접 회고 가능한 조치 | 문제·판단의 서술 방식 | 결과로 주장할 수 있는 범위 |
|---|---|---|---|
| Figma → 기능/데이터 요구 | 화면 정보 분석 및 입력/조회/저장 구분 | 화면만으로 백엔드 요구가 완전히 명세되지 않는다는 일반적 과제; 실제 충돌은 미확인 | 요구사항 분석·명세를 **수행한 경험** |
| Jira Epic/Story/Task | 업무 분해·구조화 | 구현 전 작업 세분화 필요성이라는 일반적 설계 배경 | Jira 기반 협업 프로세스 이해/활용 경험 |
| ERD·DB·SQL·DTO | 관계 데이터·쿼리·전달 구조 초안 | 화면의 데이터와 DB/API 전달값 연결 필요성; 실제 장애 해결은 미확인 | 데이터 구조 **설계/작성 경험**; 실제 반영/운영 미확정 |

**주의:** 위 3건은 한 실습의 관련 업무를 설명하기 위해 나눈 것이다. **별도의 운영 장애 3건을 스스로 발견하고 해결한 사례**라는 주장은 만들지 않는다.

## 4. 출처 누락/추가 회고용 검증 질문

추가 인터뷰가 가능해지면 구체적인 문제/판단을 복원하기 위한 **단일 대표 사례**부터 선택하는 것이 효율적이다.

1. **DealFlow의 업무 목적:** 단순 사내 할 일/업무 추적 서비스인가, 거래/영업/고객/문서 등을 다루는 다른 서비스인가? 명칭만으로 단정 불가.
2. **본인에게 할당된 Figma 화면 하나:** 무엇을 입력하고 어디에서 보고 무엇을 변경/저장하는 화면이었나?
3. **DB 엔터티 하나:** 사용자·업무·상태·이력 등의 실재 엔터티 중 기억나는 것이 있나? 예시는 추정치이므로 실제 사실로 적지 않음.
4. **SQL과 DTO의 종류:** DDL인가 조회/변경 SQL인가? Java/Kotlin/Python/TypeScript 중 확인되는 언어나 프레임워크가 있었나?
5. **작업 결과:** 누가 어느 설계 산출물을 리뷰했고 피드백은 무엇이었나? 수정·제출·구현 연결이 있었나?
6. **업무 진행 방식:** 교육 과제인지 실제 팀이 사용할 설계인지, 동료와 어떤 경계로 역할이 나뉘었나?

## 5. 채용 문장 사용 정책

**미확인으로 제외:** “제품 핵심 기능 출시”, “백엔드 API 구현·배포 주도”, “수십 개 테이블/엔드포인트 설계”, “N% 개발 효율 개선”, “의료 AI/영상모델 구현”, “DB 쿼리 성능 개선”, “테스트 자동화” 등.

**표기 원칙:** 후속 회고에서 실제 화면/필드/기능과 일치 여부를 확인하면 M2 → 강화된 회고 내용으로 업데이트한다. 원본 코드·현장 문서가 복구되지 않는 한 **외부 검증된 정량 성과로 바꾸지는 않는다**.

원본 문서 [beamworks.md](beamworks.md)는 바로 활용 가능한 **상황 → 문제 → 판단 → 조치 → 결과** 서사이며, 이 원장은 그 서사의 불확실성을 기록한다.
