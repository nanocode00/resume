# Beamworks 현장실습 — 기억 근거·미확인 항목 원장

> **2026-10-29 기억 기반 경험 복원(v0.2).** 프로젝트 원본 저장소·회사 비공개 파일·Figma·Jira 티켓·Bitbucket·ERD·SQL·DTO·실습일지·리뷰 로그를 확인하지 못했다. **자료를 찾지 못했다**는 것이 **과거에 존재하지 않았음**을 뜻하지는 않는다. 공개 이력서에 회사 내부 데이터·화면·비공개 세부 내용을 재현하지 않는다.

## 1. 근거 등급

- **M1 — 일관된 과거 자기보고(문서로 보존):** resume 저장소에 이미 있던 experiences/beamworks.md, resume.md, career-timeline.md 및 이후 정리된 포트폴리오 요약이 공통적으로 언급한 작업. 실제 현장 산출물은 확인되지 않았으므로 **독립 검증은 아님**.
- **M2 — 기존 회고 메모:** 2026-01-01~28 기간, 신규 프로젝트 DealFlow, 2026-01-19 OJT 관련 메모, Git/Jira/Bitbucket 교육, Figma 요구사항→명세/ERD/SQL/DTO 정리. 개별 날짜·정확한 업무 프로세스는 당시 원본으로 확인되지 않았다.
- **M3 — 2026-10-29 본인 직접 보충 회고:** 빔웍스는 **의료기기 회사**이며 DealFlow는 **병원을 고객으로 하는 사내 고객관리(CRM) 플랫폼**. 플랫폼에서 관리하는 기능/정보 영역으로 **병원 정보, 병원 내 담당자, 데모 정보, 초음파 기기 정보, 고객의 소리(VOC)**를 구체적으로 언급. 이는 **프로젝트 도메인에 대한 직접 기억**이지, 회사 측 원본 문서에 의한 독립 검증이나 개별 영역 구현자 확인은 아니다.
- **I — 일반적인 개발 설계 문제에서의 추론:** “UI만으로 입력·조회·저장 경계를 알 수 없다”, “업무를 작은 작업 단위로 나눠야 한다” 등의 배경 설명. 이는 기술적 개연성이 있는 **서사 구조**이지 실제로 발견한 결함, 특정 동료와의 갈등, 문제 수정이 있었다는 기록이 아니다.
- **U — 미확인/금지 표현:** 직접 맡은 화면의 이름과 범위, 정확한 필드·테이블·FK 수, DB 종류, 쿼리 종류, DTO 언어, 티켓 수, 릴리즈 기여, 자동 테스트, 리뷰 수, 생산성 향상, 의료영상 모델 담당 등. **관리 대상 영역이 알려진 것**과 **실제 ERD/테이블이 확인된 것**을 분리한다.

### 시간·프로젝트의 정확한 진술

- “2026.01 · 4주” 및 구체적 시작/종료일은 회고 기록과 일치하는 범위에서 작성.
- **DealFlow가 병원 고객관리(CRM) 플랫폼**이었다는 점과 **병원·담당자·데모·초음파 기기·VOC를 관리하는 체계가 있었다는 점**은 2026-10-29 사용자 직접 회고로 구체화됐다. 다만 **회사 내부 공식 문서·운영 시스템을 재확인한 것은 아니며**, 정식 상용 서비스·배포·실제 운영 여부, 사용자의 직접 구현 모듈은 계속 미확정이다.
- **Git·Jira·Bitbucket 교육의 존재**와 **그 도구로 실습용/실제 운영 코드를 작성·병합했다는 사실**은 서로 다른 주장이다.

## 3. 5단계 사례의 사실과 해석 분리

| 사례 | 직접 회고 가능한 조치 | 문제·판단의 서술 방식 | 결과로 주장할 수 있는 범위 |
|---|---|---|---|
| Figma → 기능/데이터 요구 | 병원 고객 CRM의 화면 정보 분석 및 입력/조회/저장 구분 | 관리 영역 5종은 M3에 해당, 개인 담당 화면은 미확정. 화면만으로 백엔드 요구가 모두 명세되지 않는다는 일반적 과제 | 요구사항 분석·명세를 **수행한 경험** |
| Jira Epic/Story/Task | 업무 분해·구조화 | 구현 전 작업 세분화 필요성이라는 일반적 설계 배경 | Jira 기반 협업 프로세스 이해/활용 경험 |
| ERD·DB·SQL·DTO | CRM 요구의 데이터 구조·쿼리·전달 구조 초안 | 병원/담당자/데모/장비/VOC 관리 영역이 실제 테이블/DTO 각각과 일대일 대응했다고 **가정하지 않음** | 데이터 구조 **설계/작성 경험**; 실제 반영/운영 미확정 |

**주의:** 위 3건은 한 실습의 관련 업무를 설명하기 위해 나눈 것이다. **별도의 운영 장애 3건을 스스로 발견하고 해결한 사례**라는 주장은 만들지 않는다.

## 4. 출처 누락/추가 회고용 검증 질문

추가 인터뷰가 가능해지면 구체적인 문제/판단을 복원하기 위한 **단일 대표 사례**부터 선택하는 것이 효율적이다.

1. **개인 담당 업무 영역:** 병원 / 병원 내 담당자 / 데모 / 초음파 기기 / VOC 중 **실제로 명세서·Jira 티켓·ERD·SQL·DTO를 작성한 범위**는 어디였는가?
2. **대표 Figma 화면 한 개:** 병원/담당자/데모/장비/VOC 중 어떤 화면을 맡았고 어떤 입력값·조회값·저장값을 정의했는가?
3. **대표 설계 결정 한 건:** 어떤 정보를 별도 테이블로 나눴는지 또는 데이터의 필수 여부·관계를 어떻게 판단했는가? **테이블/필드명을 추측하지 않음**.
4. **SQL과 DTO의 종류:** DDL인가 조회/변경 SQL인가? Java/Kotlin/Python/TypeScript 중 확인되는 언어나 프레임워크가 있었나?
5. **작업 결과:** 누가 어느 설계 산출물을 리뷰했고 피드백은 무엇이었나? 수정·제출·구현 연결이 있었나?
6. **업무 진행 방식:** 교육 과제인지 실제 팀이 사용할 설계인지, 동료와 어떤 경계로 역할이 나뉘었나?

## 5. 채용 문장 사용 정책

**허용(기억 기반):** “병원·담당자·데모·초음파 기기·VOC 정보를 다루는 **사내 CRM DealFlow** 현장실습에서 Figma 화면의 입력·조회·저장 데이터 요구를 분석하고 Jira Epic/Story/Task 구조, ERD·DB 테이블·SQL·DTO 설계로 구체화한 경험”.

**미확인으로 제외:** “병원·담당자·데모·장비·VOC 다섯 모듈 전체를 직접 개발”, “VOC 접수/처리 워크플로를 직접 설계·운영”, “제품 핵심 기능 출시”, “백엔드 API 구현·배포 주도”, “수십 개 테이블/엔드포인트 설계”, “N% 개발 효율 개선”, “의료 AI/영상모델 구현”, “DB 쿼리 성능 개선”, “테스트 자동화” 등.

**표기 원칙:** 이번 보충으로 CRM 목적과 관리 영역은 **M3(직접 보충 회고)**로 갱신했다. 후속 회고에서 본인이 맡은 화면/필드/기능을 구체화해도 원본 없는 자기보고라는 성격은 유지한다. 원본 코드·현장 문서가 복구되지 않는 한 **외부 검증된 정량 성과로 바꾸지는 않는다**.

원본 문서 [beamworks.md](beamworks.md)는 바로 활용 가능한 **상황 → 문제 → 판단 → 조치 → 결과** 서사이며, 이 원장은 그 서사의 불확실성을 기록한다.
