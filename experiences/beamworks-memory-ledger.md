# Beamworks 현장실습 — 기억 근거·미확인 항목 원장

> **2026-10-29 기억 기반 경험 복원(v0.3).** 프로젝트 원본 저장소·회사 비공개 파일·Figma·Jira 티켓·Bitbucket·ERD·SQL·DTO·실습일지·리뷰 로그를 확인하지 못했다. **자료를 찾지 못했다**는 것이 **과거에 존재하지 않았음**을 뜻하지는 않는다. 공개 이력서에 회사 내부 데이터·화면·비공개 세부 내용을 재현하지 않는다.

## 1. 근거 등급

- **M1 — 일관된 과거 자기보고(문서로 보존):** resume 저장소에 이미 있던 experiences/beamworks.md, resume.md, career-timeline.md 및 이후 정리된 포트폴리오 요약이 공통적으로 언급한 작업. 실제 현장 산출물은 확인되지 않았으므로 **독립 검증은 아님**.
- **M2 — 기존 회고 메모:** 2026-01-01~28 기간, 신규 프로젝트 DealFlow, 2026-01-19 OJT 관련 메모, Git/Jira/Bitbucket 교육, Figma 요구사항→명세/ERD/SQL/DTO 정리. 개별 날짜·정확한 업무 프로세스는 당시 원본으로 확인되지 않았다.
- **M3 — 2026-10-29 본인 직접 보충 회고:** 빔웍스는 **의료기기 회사**이며 DealFlow는 **병원을 고객으로 하는 사내 고객관리(CRM) 플랫폼**. 플랫폼에서 관리하는 기능/정보 영역으로 **병원 정보, 병원 내 담당자, 데모 정보, 초음파 기기 정보, 고객의 소리(VOC)**를 구체적으로 언급. 이는 **프로젝트 도메인에 대한 직접 기억**이지, 회사 측 원본 문서에 의한 독립 검증이나 개별 영역 구현자 확인은 아니다.
- **M4 — 2026-10-29 개인 수행 범위 직접 재확인:** **디자이너가 Figma에 설계한 목업 UI를 분석해 제품 전체의 필요한 데이터 구조를 도출**하고, **ERD → SQL → DTO를 직접 작성**했음. 일련의 작업 진행을 **Jira로 관리**. M3의 '관리 범위 5개'와 결합해 **설계 담당 범위는 전체 제품**으로 특정됨. 이는 **직접 구현한 백엔드 서비스·전체 UI 제작·실제 운영 DB 적용을 입증하지 않는다**.
- **I — 일반적인 개발 설계 문제에서의 추론:** “UI만으로 입력·조회·저장 경계를 알 수 없다”, “업무를 작은 작업 단위로 나눠야 한다” 등의 배경 설명. 이는 기술적 개연성이 있는 **서사 구조**이지 실제로 발견한 결함, 특정 동료와의 갈등, 문제 수정이 있었다는 기록이 아니다.
- **U — 미확인/금지 표현:** 개별 화면의 상세 이름/필드/키·테이블·FK 수, DB 종류, SQL 종류, DTO 언어, Jira 티켓 건수, 산출물 리뷰·승인 및 코드·운영 DB에 실제 반영되었는지, 릴리즈·자동 테스트·생산성 향상·의료영상 모델 담당 등. **설계 담당은 제품 전체로 확인됐으나 실제 기능 구현이나 런타임 운영 결과는 별개**다.

### 시간·프로젝트의 정확한 진술

- “2026.01 · 4주” 및 구체적 시작/종료일은 회고 기록과 일치하는 범위에서 작성.
- **DealFlow의 병원 CRM 목적과 병원·담당자·데모·초음파 기기·VOC라는 관리 범위**는 M3에 해당한다. **본인이 제품 전체 Figma 목업의 요구 데이터 분석과 ERD→SQL→DTO 작성, Jira 작업 관리를 담당했다는 사실**은 M4에서 직접 확인됐다. 다만 **회사 내부 공식 문서·운영 시스템을 재확인한 것은 아니며**, 정식 출시·배포·운영 코드 반영 여부는 계속 미확정이다.
- **Git·Jira·Bitbucket 교육의 존재**와 **그 도구로 실습용/실제 운영 코드를 작성·병합했다는 사실**은 서로 다른 주장이다.

## 3. 5단계 사례의 사실과 해석 분리

| 사례 | 직접 회고 가능한 조치 | 문제·판단의 서술 방식 | 결과로 주장할 수 있는 범위 |
|---|---|---|---|
| Figma → 기능/데이터 요구 | **디자이너 목업을 제품 전체에 걸쳐 분석**하여 필요한 데이터를 파악 | 관리 영역 5종은 M3, 개인 설계 범위 전체는 M4. 목업만으로 DB 구조가 완성되지 않는다는 일반적 설계 과제 | **제품 전체 UI 기반 데이터 분석을 직접 수행** |
| Jira Epic/Story/Task | ERD→SQL→DTO를 작성하는 **자신의 진행 작업을 Jira로 관리** | Jira 티켓 혼선 같은 실제 장애가 발생했다는 증거는 없음 | **Jira로 설계 작업을 관리한 경험** |
| ERD → SQL → DTO | **제품 전체 목업에서 도출한 데이터 구조를 ERD로 정리한 다음 SQL과 DTO 작성** | 다섯 관리 영역을 각 1개 테이블이나 DTO로 대응시켰다고 가정하지 않음 | **개인 설계 산출물 작성**; 실제 반영/운영 미확정 |

**주의:** 위 3건은 한 실습의 관련 업무를 설명하기 위해 나눈 것이다. **별도의 운영 장애 3건을 스스로 발견하고 해결한 사례**라는 주장은 만들지 않는다.

## 4. 출처 누락/추가 회고용 검증 질문

추가 인터뷰가 가능해지면 구체적인 문제/판단을 복원하기 위한 **단일 대표 사례**부터 선택하는 것이 효율적이다.

1. **제품 전체 설계 범위는 확인됨.** 선택적으로 병원/담당자/데모/기기/VOC의 관계 중 기억나는 **구체 데이터 모델 결정 하나**는 무엇인가?
2. **대표 Figma 화면 한 개:** 디자이너가 만든 목업 중 어떤 화면에서 데이터 항목의 입력·조회·저장 규칙을 어떻게 분석했는가? 전체를 맡았다는 사실은 더 이상 질문하지 않음.
3. **대표 설계 결정 한 건:** 어떤 정보를 별도 테이블로 나눴는지 또는 데이터의 필수 여부·관계를 어떻게 판단했는가? **테이블/필드명을 추측하지 않음**.
4. **SQL과 DTO의 종류:** DDL인가 조회/변경 SQL인가? Java/Kotlin/Python/TypeScript 중 확인되는 언어나 프레임워크가 있었나?
5. **작업 결과:** 누가 어느 설계 산출물을 리뷰했고 피드백은 무엇이었나? 수정·제출·구현 연결이 있었나?
6. **협업·검토 범위:** 디자이너 목업과 본인 데이터 설계의 경계는 확인됨. 실제 팀에 제출·검토된 경로나 동료 피드백, Jira 완료 처리 수준은 무엇이었나?

## 5. 채용 문장 사용 정책

**허용(기억 기반):** “병원·담당자·데모·초음파 기기·VOC 정보를 다루는 **사내 CRM DealFlow**에서 디자이너의 **제품 전체 Figma 목업**을 분석해 필요한 데이터 구조를 도출하고 **ERD→SQL→DTO를 직접 작성**했으며, 해당 작업을 **Jira로 관리**했다”. 설계 전체 범위는 M4로 확인됨.

**미확인으로 제외:** “병원·담당자·데모·장비·VOC 다섯 모듈 전체를 직접 **코딩·출시**”, “VOC 처리 워크플로 실제 운영”, “제품 핵심 기능 출시”, “백엔드 API 구현·배포 주도”, “수십 개 테이블/엔드포인트 설계”, “N% 개발 효율 개선”, “의료 AI/영상모델 구현”, “DB 쿼리 성능 개선”, “테스트 자동화” 등. **제품 전체 설계와 전체 소프트웨어 구현의 차이를 명확히 유지**한다.

**표기 원칙:** CRM 도메인·관리 영역은 **M3**, **제품 전체 Figma 분석 → ERD→SQL→DTO 작성 + Jira 진행 관리라는 본인 업무 범위**는 **M4**에 해당한다. 원본 없는 자기보고라는 성격은 그대로 유지하며 외부 검증된 정량 성과로 바꾸지는 않는다. 원본 코드·현장 문서가 복구되지 않는 한 **외부 검증된 정량 성과로 바꾸지는 않는다**.

원본 문서 [beamworks.md](beamworks.md)는 바로 활용 가능한 **상황 → 문제 → 판단 → 조치 → 결과** 서사이며, 이 원장은 그 서사의 불확실성을 기록한다.
