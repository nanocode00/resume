## 0. 작업 단위 복원 원칙

사용자가 원한 핵심은 프로젝트 전체를 한 번에 재구성하는 것이 아니라, 실제 개발 경험을 다음 형식의 **작업 단위**로 하나씩 복원하는 것이다.

`현상/문제 → 원인과 제약 → 해결 방향을 선택한 이유 → 구체 구현 → 검증과 결과`

진행 원칙:

1. GitHub 코드·커밋과 자료에서 작업 흔적을 하나 찾는다.
2. 하나의 작업 단위 초안을 위 구조로 작성한다.
3. 코드가 증명하는 사실과 사용자 기억이 필요한 사실을 분리한다.
4. 사용자에게 당시 상황과 의사결정을 확인한다.
5. 확인이 끝난 작업만 확정 목록에 누적한다.
6. 실제 개발 시점 순서대로 진행한다.
7. 충분히 쌓인 뒤 `experiences/hummingblocks.md`와 `resume.md`를 다시 구성한다.

기존 전체 재작성 Draft PR은 참고 초안으로만 유지하고 merge하지 않는다.

## 1. 역할·연대기 기본 확인

- 2022.10~2023.03의 Python/Tkinter·PyQt·pygame·OpenCV DNN 프로토타입 커밋은 다른 팀원 명의다.
- 재훈님의 첫 Android 커밋 `cede7ee`(2023-03-20)는 초기 앱 전체와 `camtest1`, `acctest`를 일괄 추가했다.
- 2026-09-12 사용자 확인을 통해 `cede7ee`의 초기 Android 코드는 모두 재훈님이 직접 구현한 것으로 확정했다.
- 최종 제품은 처음부터 Android로 개발할 계획이었고, 선행 Python 프로그램은 Android 개발 전에 기능과 사용 흐름을 보여주기 위한 미완성 데모용 프로토타입이었다.
- Play·Loop·Star, 좌·우·else 조건, 악기 레벨·연산 등 블록 규칙은 팀 회의에서 재훈님이 주로 설계 의견을 냈고, 초기 Python 인터프리터 코드와 테스트는 다른 팀원이 담당했다.
- Git 커밋일만으로는 `cede7ee` 내부 기능들의 실제 작성 순서를 증명할 수 없으므로, 초기 일괄 구현은 사용자 흐름·기술 의존 순서로 정리하고 이후 작업은 실제 커밋 시점 순으로 진행한다.

## 2. 확정 작업 단위

### HB-E01 — 초기 Android 앱 구조와 사용자 흐름 구현

- **배경:** Python 데모 이후 최종 제품인 Android 앱의 기본 사용자 흐름을 실제 모바일 UI로 구현해야 했다.
- **기획 역할:** `Loading → Main → 장르 선택 → 촬영 → 재생 → 재촬영/홈` 흐름 자체는 팀 회의에서 결정했다.
- **개인 구현:** `LoadingActivity`, `MainActivity`, `SelectActivity`, `ScanActivity`, `PlayActivity`로 역할을 나누고 `Intent`, Activity Result, 권한 처리, 화면 간 상태 전달을 구현했다.
- **표현 원칙:** `사용 흐름을 단독 설계`가 아니라 `팀에서 합의한 제품 흐름을 Android Activity 구조로 구현하고 화면 간 상태·결과 전달을 연결`한 작업으로 쓴다.

### HB-E02 — 카메라 preview·촬영 기능 분리 검증 및 제품 통합

- **목표:** 실물 코딩 블록을 앱에서 직접 촬영하기 위한 카메라 입력 기능이 필요했다.
- **접근:** 제품 앱에 바로 섞기보다 `camtest1`이라는 독립 테스트 모듈에서 카메라 기능만 먼저 구현·시험했다.
- **구현:** `SurfaceView + SurfaceHolder.Callback`으로 camera open, preview, capture, release 생명주기를 처리하고 카메라/저장소 권한과 `Camera.takePicture()` 촬영을 검증했다.
- **통합:** 검증한 구조를 제품 앱의 `CameraSurfaceView`와 `ScanActivity`에 옮겼다.
- **표현 원칙:** `별도 테스트 모듈에서 위험 요소를 먼저 검증한 뒤 제품 코드로 통합`한 개발 방식으로 정리한다.

### HB-E03 — 촬영 이미지 파일화 및 Python/OpenCV 인식 경로 연결

- **초기 촬영 전제:** 초기 UX는 휴대폰을 왼쪽으로 90도 돌린 방향을 기준으로 했고, 촬영 bitmap에는 고정 `90°` 회전 보정을 적용했다.
- **파일화 이유:** Python/OpenCV 인식 코드가 `cv2.imread(path)` 형태로 실제 이미지 파일 경로를 필요로 했기 때문에 촬영 이미지를 앱 cache의 JPEG 파일로 저장했다.
- **연결:** `ScanActivity`에서 cache JPEG의 절대 경로 `imgPath`를 Python `main(imgPath)`에 전달해 인식과 실행 가능 여부를 검사했다.
- **초기 실행 데이터 흐름:** 성공하면 `PlayActivity`를 열고, 당시 구조에서는 인식 데이터를 Intent로 직접 넘기기보다 Python 모듈에 유지된 상태를 `PlayActivity`가 `play(count, direction)`으로 조회해 음악 실행 데이터로 사용했다.
- **후속 문제:** 휴대폰을 다른 방향으로 들면 촬영 이미지 방향이 달라져 인식이 실패하는 문제가 발생했다.
- **후속 개선 분리:** 초기에는 중력센서 기반 3방향(0/90/180°), 이후 CameraX 개편에서는 `OrientationEventListener` 기반 4방향(0/90/180/270°) 보정으로 확장됐다. 이 동적 방향 보정은 별도 후속 작업으로 다룬다.

### HB-E04 — 중력센서 기반 left/right 조건 입력 구현

- **기획:** 제품 기획 단계에서 `left/right` 조건은 사용자가 휴대폰을 왼쪽/오른쪽으로 기울여 입력하는 것으로 정해져 있었다.
- **검증:** 별도 `acctest` 모듈에서 `TYPE_GRAVITY` 센서의 x/y/z 값과 중력 벡터를 이용해 x/y 기울기 각도를 계산하는 방식을 먼저 시험했다.
- **제품 구현:** `PlayActivity`에서 x축 기울기 각도에 임계값을 적용해 `LEFT / RIGHT / MIDDLE` 상태로 변환하고 조건 분기 입력으로 사용했다.
- **피드백:** 기울기 상태에 따라 지휘자 이미지와 좌·우 화살표 UI도 변경해 현재 입력 상태를 보여줬다.
- **표현 원칙:** `기울기 UX를 단독 기획`한 것이 아니라 `팀 기획의 물리 입력을 Android 중력센서 기반 로직으로 구현해 실행 상태와 UI에 연결`한 작업으로 쓴다.

### HB-E05 — 향후 멀티 장르를 고려한 장르 선택 구조 구현

- **배경:** 완전 초기에는 실제 음악 콘텐츠가 한 세트뿐이었지만 이후 여러 장르 음악을 추가할 계획이 있었다.
- **목표:** 향후 음악 콘텐츠가 늘어날 때 사용자가 장르를 선택하고 선택 상태를 앱 전반에서 사용할 수 있는 구조를 미리 만들어두는 것이었다.
- **구현:** `SelectActivity`에 `RecyclerView` 기반 장르 목록과 단일 선택 상태를 구현하고, 선택값을 `Common.current_genre`로 관리해 `MainActivity`와 `PlayActivity`에서 표시할 수 있도록 연결했다.
- **코드 확인:** 초기 `Common.genre_list`에는 `재즈`, `클래식`, `힙합`, `롹` 4개 항목이 정의돼 있었지만, 초기 음악 실행 로직은 장르별 음원 세트를 선택하지 않고 한 세트의 악기 음원을 사용했다.
- **해석:** 따라서 초기 시점에 `여러 장르 음악을 실제 지원했다`고 쓰지 않고, `향후 멀티 장르 확장을 고려해 선택·상태 관리 구조를 먼저 구현했다`고 표현한다.
- 실제 초기 음원의 음악적 장르가 팝이었다는 사용자 기억은 코드 파일명만으로는 독립 검증하지 않으며, 필요 시 당시 자료와 함께 확인한다.

## 3. 후속 확인 메모 — 화면비 대응

- 일반 스마트폰에서는 큰 문제가 없었지만 태블릿에서는 버튼이 상대적으로 작게 보였고, Z Flip 펼침 화면에서는 버튼 영역 부족으로 텍스트가 보이지 않는 문제가 있었다. 특히 홈/메인 화면의 깨짐이 가장 큰 이슈였다.
- 대응 후보로 `LinearLayout`의 컴포넌트 비율 배치와 `ConstraintLayout` percentage `Guideline` 방식을 비교했다.
- 여러 버튼·이미지의 상대 위치를 세밀하게 유지해야 하는 화면 특성상 재훈님이 `Guideline` 방식이 더 적합하다고 판단해 선택했다.
- 코드상 2023-04-25 `4fb4957`에서는 `PlayActivity` 레이아웃이 고정 dp/margin에서 9:16 콘텐츠 영역 + percentage Guideline 구조로 전환됐다.
- 사용자 기억상 홈/메인 화면 문제가 가장 컸으므로 실제 Main 화면 적용 커밋을 별도로 찾아야 한다.
- `모든 기기 지원`이라고 단정하기보다 적용 범위와 테스트 기기를 확인한 뒤 표현한다.

## 5. 작성 원칙

- 팀 전체 결과를 개인 단독 성과처럼 쓰지 않는다.
- 최신 회사 실적을 2022~2023년 개인 개발 성과처럼 쓰지 않는다.
- Android runtime을 `PyTorch native`라고 표현하지 않는다. 확인된 제품 경로는 Chaquopy + Python/OpenCV DNN + Darknet weight/cfg 구조다.
- 전체 YOLO 모델 학습을 혼자 담당했다고 확정하지 않는다.
- 9.1초/5.4초와 90%/57%는 원본 benchmark가 발견되기 전까지 `당시 기록값`으로 구분한다.
- 정확한 augmentation 방식은 원본 자료를 찾기 전까지 단정하지 않는다.
- 이력서에는 결과뿐 아니라 대안 비교와 선택 기준도 함께 남긴다.

`main`은 수정하지 않았다. 기존 변경은 Draft PR에만 있으며, 작업 단위 검증 완료 전에는 merge하지 않는다.
