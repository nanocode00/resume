## 0. 2026-09-12 방향 수정

사용자가 원한 핵심은 프로젝트 전체를 한 번에 재구성하는 것이 아니라, 실제 개발 경험을 다음 형식의 **작업 단위**로 하나씩 복원하는 것이다.

`현상/문제 → 원인과 제약 → 해결 방향을 선택한 이유 → 구체 구현 → 검증과 결과`

진행 원칙:

1. GitHub 코드·커밋과 Drive 자료에서 작업 흔적을 하나 찾는다.
2. 하나의 작업 단위 초안을 위 구조로 작성한다.
3. 코드가 증명하는 사실과 사용자 기억이 필요한 사실을 분리한다.
4. 사용자에게 화면·상황·검증 방법을 확인한다.
5. 확인이 끝난 작업만 확정 목록에 누적한다.
6. 충분히 쌓인 뒤 `experiences/hummingblocks.md`를 구성한다.
7. 가장 강한 작업 단위만 골라 마지막에 `resume.md`로 압축한다.

기존 전체 재작성 Draft PR은 방향을 비교하기 위한 **참고 초안**으로만 유지하고 merge하지 않는다. 사용자 확인 전에는 추가 문서 재작성도 진행하지 않는다.

### 작업 단위 1 — 음악 실행 화면의 기기별 비율 대응 (검증 중)

현재 코드로 확인된 사실:

- 대상 화면은 우선 `PlayActivity`의 `activity_play.xml`이다. 홈/메인 화면에도 동일한 작업을 했는지는 추가 확인이 필요하다.
- 2023-04-25 커밋 `4fb4957`의 메시지는 `testing screen support in playactivity`다.
- 변경 전에는 주요 UI 요소가 고정 `dp` 크기와 margin을 사용했다.
- 변경 후 콘텐츠 영역에 `9:16` 비율을 적용하고, 주요 View의 width/height를 `0dp`로 바꿨다.
- 위치와 크기는 `ConstraintLayout Guideline`의 `layout_constraintGuide_percent` 값으로 정의했다.
- 정사각형이어야 하는 버튼에는 `1:1` dimension ratio를 적용했다.
- 해당 커밋은 `activity_play.xml` 한 파일에서 고정 크기·margin 64개를 제거하고 percentage Guideline 88개를 추가한 대규모 비율 기반 레이아웃 전환이다.
- 2024-12-04 `play screen button size adjust` 커밋들에서도 동일한 percentage Guideline 구조를 유지하면서 버튼 위치·크기를 보정했다.

현재 작업 단위 초안:

- **현상:** 기준 기기에서는 정상인 음악 실행 화면이 다른 화면 크기·비율의 기기에서 요소 크기와 상대 위치가 어긋났다.
- **판단:** 악기·캐릭터·조작 버튼처럼 겹쳐 배치되는 요소들의 상대적인 기하관계를 유지해야 했고, 기기별 레이아웃을 따로 관리하기보다 하나의 논리적 화면을 비례 확대·축소하는 편이 적합했다.
- **구현:** `ConstraintLayout` 안에 9:16 콘텐츠 영역을 만들고, 고정 `dp/margin` 배치를 percentage `Guideline` 네 방향 제약과 `0dp` 크기로 전환했다. 정사각형 버튼은 `1:1` 비율을 추가했다.
- **코드가 보장하는 결과:** 실제 화면 크기가 달라져도 각 요소의 크기와 위치가 9:16 콘텐츠 영역에 비례해 함께 조정되는 구조가 됐다.
- **사용자 확인이 필요한 결과:** 어떤 기기·화면비에서 문제가 발생했고, 수정 후 어떤 기기에서 깨짐이 사라졌는지. 이 확인 전에는 `모든 기기를 지원했다`보다 `다양한 화면비에서 일관된 배치를 확보했다`로 표현한다.

확인 질문:

1. 문제가 난 화면이 악기와 지휘자가 보이는 `PlayActivity`였는가, 홈/메인 화면에도 같은 방식을 적용했는가?
2. 문제가 발생했거나 수정 후 테스트한 기기·해상도·화면비가 기억나는가?

현재 직접 기여 후보:

- Android 앱 개발
- Camera/CV inference integration
- YOLO 결과 후처리
- 음악 실행 로직
- UI·접근성 기능
- 출시 후 유지보수와 데이터 migration
- 데이터 라벨링 및 현장 인식 문제 피드백

팀 또는 외부 기여로 분리할 후보:

- YOLO 모델 학습 전체
- 실물 블록 설계·제조
- 디자인 제작
- 음원 제작

### 4.4 Engineering Case 1 — 검출 결과를 실행 가능한 프로그램으로 변환

- YOLO 출력인 class/confidence/bounding box를 수신
- 좌표 기준 정렬과 행·열 그룹화
- 블록 순서, 반복, 조건, 기울기, BPM, 악기 의미 해석
- 실행 전 유효성 검사
- 정상 실행이 어려운 입력을 오류·경고 코드로 분류하고 사용자 안내

현재 문서의 `왜 YOLO를 사용했는가`, `검출 결과를 실행 규칙으로 바꾸기`, `예외 처리 22가지`를 하나로 합친다.

### 4.5 Engineering Case 2 — 모바일 추론 최적화와 롤백

- 기존 Chaquopy + Python/OpenCV DNN 경로
- Galaxy S9+ 기준 평균 9.1초라는 기록
- 별도 `app_develop_tflite` 브랜치에서 Java/TFLite 전환
- 416×416 전처리, confidence filtering, class별 NMS, 좌표 후처리 이식
- NNAPI → GPU → CPU fallback 실험
- 처리 시간 9.1초 → 5.4초, 약 40.7% 단축
- 정확도 90% → 57%, 33%p 하락
- 오인식 비용을 고려해 기존 runtime 유지

이 사례는 상세 문서에서 한 번만 충분히 설명하고, 상단 요약과 이력서에는 결론만 압축한다.

### 4.6 Engineering Case 3 — 음악 실행과 콘텐츠 생성

- 여러 악기 트랙의 재생 스케줄링
- BPM에 따른 section 길이와 진행률 계산
- pause/resume 시 현재 phase와 남은 delay 복원

- 녹화 영상 concat 및 음악 mux
- 저장된 음악과 사용자 콘텐츠 관리

## 5. 현재까지 확인된 내용

### 코드에서 확인된 큰 흐름

- `app_develop`에는 제품 앱, 별도의 시각장애인용 모듈, 음악 asset pack, Camera/CV, 저장·녹화·migration 관련 구현이 존재한다.
- mainline에는 `Runner.java`가 Python `Classifier.py`를 호출하는 Chaquopy 기반 경로가 남아 있다.
- `app_develop_tflite`에는 TFLite 모델과 Java `Classifier`를 사용한 별도 구현 흔적이 있다.
- 저장소에는 TFLite 테스트, 음악 재생 테스트, UX 테스트 등 여러 실험 모듈이 남아 있다.
- 제품이 한 번의 프로토타입으로 끝난 것이 아니라 기능이 장기간 확장된 흔적이 확인된다.

### Camera → inference → 실행 규칙 경로 검증 결과

#### 제품 브랜치 `app_develop`

- `CameraActivity.java`가 촬영 파일 경로와 Darknet `weights/cfg` 경로를 Python 모듈에 전달한다.
- `Runner.java`가 Chaquopy로 `Classifier.py`의 `classify`를 호출한다.
- `Classifier.py`는 OpenCV DNN으로 416×416 입력을 추론하고 confidence filtering·NMS를 수행한다.
- Python에서 bounding box를 x/y 좌표 기준으로 정렬·그룹화한 뒤 class ID 묶음을 Java에 반환한다.
- Java `Runner.java`는 PLAY/LOOP/STAR, 좌·우 기울기 조건, ELSE, 악기 레벨 연산 등을 실행 가능한 상태로 해석하고 유효성을 검사한다.

#### 실험 브랜치 `app_develop_tflite`

- `7cdc9e1` 커밋에서 Chaquopy/Python 의존성을 제거하고 Java `Classifier.java`와 TensorFlow Lite 경로를 추가했다.
- 416×416 RGB float 입력, confidence filtering, class별 NMS, IoU 계산, NNAPI → GPU → 4-thread CPU fallback이 코드로 확인된다.
- 좌표 그룹화와 실행 규칙 해석도 Java `Runner.java`로 옮겼다.
- `fc771fd` 커밋은 촬영 bitmap의 비율 유지, 중앙 정렬, 좌우 padding 방식으로 전처리를 보정했다. 커밋 메시지는 `update 1.0.2(undone)`이다.
- 같은 날 `1bb3f7c` 커밋에서 제품 브랜치가 Java/TFLite 코드를 제거하고 Chaquopy/Python 경로를 복원했다.
- 현재 브랜치 비교에서도 TFLite tip은 제품 mainline에 합쳐지지 않은 독립 실험으로 남아 있다.

따라서 이력서에는 `TFLite를 검토했다`보다 **직접 구현·비교했으며 제품 요구사항에 따라 미채택했다**고 쓰는 것이 근거에 맞다.

### 예외 개수 정정 필요

- 제품 브랜치 `Runner.java`의 `ERROR_CODE`는 0~22, 총 23종이다.
- 한국어 UI 리소스 `error_msg`도 23개이며 `warning_msg`는 별도 2개다.
- 기존 문서의 `22가지 예외`는 특정 항목을 제외한 과거 집계일 수 있으나 현재 코드와 일치하지 않는다.
- 과거 문서에서 집계 기준을 확인하기 전까지는 숫자를 확정하지 않고 `오류·경고 유형을 정의했다`로 표현한다.
