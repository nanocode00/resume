# Beamworks — 2026년 1월 현장실습 경험 복원

> **2026-10-29 기억 기반 초안(v0.2), 원본 미보유.** 이번 복원은 당시에 남겨진 원본 코드·티켓·Figma·ERD·실습일지 없이, 이전에 작성해둔 이력서/경험 문서와 이후 포트폴리오 요약 및 과거 회고를 바탕으로 한다. 따라서 구현·업무 완료·의사결정의 정확한 세부 내용은 **자기보고에 의존**하며, 확실하지 않은 내용은 가설 또는 추가 회고 질문으로 둔다. [회고 검증 원장](beamworks-memory-ledger.md) 참조.

## 한 줄 요약

**의료기기 회사 Beamworks의 병원 고객관리(CRM) 플랫폼 DealFlow 관련 현장실습(2026-01-01~01-28, 약 4주)**에서, **Figma 화면을 기준으로 입력·조회·저장 데이터와 기능 요구사항을 정리하고, Jira Epic/Story/Task, ERD, SQL, DTO에 연결하는 개발 전 설계 작업을 경험**했다.

- **프로젝트 성격(2026-10-29 직접 회고):** **DealFlow**는 병원을 고객으로 관리하는 사내 **고객관리(CRM) 플랫폼**. **병원 정보, 병원 내 담당자 정보, 데모 정보, 초음파 기기 정보, 고객의 소리(VOC)**를 관리하는 기능 영역이 있었다. 이 분류는 **플랫폼의 관리 대상**을 뜻하며, 모두 본인이 단독 구현한 모듈이나 테이블이라고 주장하지 않는다.
- **직접 작업으로 회고된 범위:** Figma 화면별 기능 분석/명세, Jira 작업 단위 구조화, draw.io를 활용한 ERD 및 DB 테이블 구상, SQL·DTO 작성.
- **OJT/환경:** Git, Jira, Bitbucket 관련 교육·온보딩이 있었다는 기존 기록. **2026-01-19 OJT 관련 메모**가 있으나 구체적으로 무엇을 실습·평가했는지, 해당 일자가 개시일인지 단일 일정인지는 확인되지 않는다.
- **명확한 제외:** 의료 AI 모델·의료영상 분석을 담당했다는 주장, 실제 제품 배포·DB 적용·API 서비스 구현 완료, 본인의 설계가 팀 생산성을 수치로 개선했다는 주장.

## 프로젝트 맥락

빔웍스는 **의료기기 회사**이고, 실습에서 다룬 DealFlow는 병원을 고객으로 관리하기 위한 **사내 고객관리(CRM) 플랫폼**이었다. 당시 직접 회고에 따라, 관리 대상으로 다음 영역을 확인할 수 있다.

| 관리 정보/기능 | 확인되는 범위 | 아직 확인되지 않은 것 |
|---|---|---|
| **병원 정보** | 병원 고객의 정보 관리 | 실제 필드명, 고유키, 병원 분류·계약 규칙 |
| **병원 내 담당자** | 병원 내부 담당자의 정보 관리 | 연락처·직책 필드, 한 병원당 담당자 수, 관계형 제약 |
| **데모 정보** | 데모 관련 정보 관리 | 데모의 정의·예약/진행/완료 상태, 장비 연결 방식 |
| **초음파 기기 정보** | 취급 초음파 장비 관련 정보 관리 | 모델명·식별번호·설치·관리 이력 등의 구체 필드 |
| **고객의 소리(VOC)** | VOC를 등록·관리할 수 있는 체계 존재 | 접수/분류/처리/종결 절차, 권한, 담당자 및 처리 이력 구현 여부 |

위의 다섯 영역은 **제품의 기능 범위**로 확인한 것이며 **실제 ERD의 테이블 목록, API, DTO, 데이터 관계 또는 개인 담당 범위로 동일시하지 않는다.** 사용자 회고에서 개별 항목의 내부 필드나 정확한 업무 흐름까지 확인된 것은 아니다.

이러한 고객 데이터가 여러 화면에서 입력·조회·저장되려면 UI 요구사항을 **기능 설명·개발 작업·데이터 모델**로 구체화해야 했다. 기존 문서에서 확인되는 개인 경험의 중심은 **Figma 화면 해석 → Jira 단위 분해 → ERD/SQL/DTO 설계**다. 실제 담당 화면, 팀원별 역할, 최종 적용/배포 여부는 아직 미확정이다.

## 경험 1 — Figma 화면을 기능·데이터 요구사항으로 읽기

### 상황
병원과 병원 내 담당자, 데모, 초음파 기기, VOC를 관리하는 **DealFlow CRM의 Figma 화면**을 바탕으로 구현에 필요한 요구사항을 정리하는 작업을 수행했다는 회고가 있다. 각 영역의 **특정 화면을 본인이 전부 담당했는지**는 확인되지 않았다.

### 문제
**UI에는 표시 요소·입력란·버튼이 표현되지만 이것만으로 어떤 데이터가 입력·조회·저장되어야 하는지 모두 명시되지는 않는다.** 이 문장은 설계 일반에서 도출한 당시 과제의 성격이며, 구체적인 요구사항 충돌이나 장애가 실제 발생했다는 뜻은 아니다.

### 판단
각 화면 요소를 단순한 디자인 컴포넌트로 취급하기보다 **입력값 / 조회값 / 저장값**의 관점에서 분류해, 백엔드에 필요한 데이터와 기능의 경계를 파악하는 방식으로 접근했다고 기존 기록에 남아 있다.

### 조치
Figma 화면을 읽고 화면별 기능 요구사항을 분석·정리했다. 입력·조회·저장 항목을 구분해 **기능 명세 작업**을 진행했다는 회고가 있다. 병원·담당자·데모·장비·VOC라는 **플랫폼의 업무 영역**은 확인되지만, 이 중 자신이 맡은 특정 화면·필드명·검증 규칙·예외 흐름은 아직 확인되지 않는다.

### 결과
Figma를 **기능 및 데이터 요구사항 관점에서 해석하고 명세한 경험**을 기록할 수 있다. 다만 정식 승인된 요구사항 문서의 개수, 실제 개발팀 적용 여부, 누락률·수정 횟수 등의 수치는 확인할 수 없어 성과로 사용하지 않는다.

## 경험 2 — Jira 기반 작업 구조화와 협업 프로세스

### 상황
실습 중 Git/Jira/Bitbucket 등 협업 도구에 대한 온보딩과 업무 단위 정리 경험이 있었다는 기록이 있다.

### 문제
여러 화면·기능을 개발하려면 화면 단위 요구를 개발 가능한 업무 단위로 구분하는 과정이 필요하다. **실제 팀에서 Jira 티켓 혼선·지연 문제가 있었다는 증거는 없음**.

### 판단
큰 기능·사용자 요구·구체 구현 작업을 구분하는 **Epic → Story → Task** 체계를 사용했다고 기존 문서에 적혀 있다.

### 조치
기능 요구사항을 Jira의 Epic, Story, Task 구조로 정리하는 작업을 경험했다. **본인이 실제 티켓을 발행·할당·완료 처리한 건수나 Jira 워크플로 설정 권한은 미확인**이다. Git/Bitbucket은 교육·실습 경험 범위까지만 기록한다.

### 결과
요구사항을 **협업·개발 단위로 분해하는 방식**을 익혔다. 작업 처리 시간 감소, 프로젝트 관리 정책 개편, CI/CD 구축, 코드 병합 권한 등은 확인되지 않은 내용이므로 주장하지 않는다.

## 경험 3 — Figma 요구를 ERD·SQL·DTO로 구체화

### 상황
병원·담당자·데모·초음파 기기·VOC 등 여러 종류의 고객 정보를 다루는 CRM의 화면 요구사항을 저장 구조와 데이터 전달 단위로 옮기는 설계 업무가 포함되었다는 회고가 있다. 다만 **이 다섯 영역 모두를 직접 모델링했는지는 확인되지 않는다**.

### 문제
UI에서 필요한 데이터가 정리되더라도 그 데이터의 저장 위치, 테이블 간 관계, 요청/응답으로 전달할 필드 구조가 없으면 구현 단위가 구체화되기 어렵다. **이 문제는 당시 수행 업무의 목적을 설명하는 것이며, 특정 DB 장애 해결 사례는 아니다**.

### 판단
화면의 **입력·조회·저장 데이터 구분을 먼저** 하고, 이를 바탕으로 **ERD / DB 테이블 / SQL / DTO**를 서로 대응시키는 방향으로 설계했다는 기존 기록이 있다.

### 조치
draw.io를 이용한 ERD 설계, DB 테이블 설계, SQL 및 DTO 정의 작성에 참여한 것으로 기억된다. **병원·담당자·데모·장비·VOC는 업무 영역으로 확인됐지만 각 영역에 대응하는 테이블 수, 실제 외래키 및 개인 작성 DTO 목록은 확인되지 않는다.** SQL의 종류(DDL/조회·수정문), 데이터베이스 엔진, DTO 언어·프레임워크, 검증·테스트 여부도 미확정이다. 'SQL 작성'은 운영 DB 반영을 의미하지 않는다.

### 결과
**화면 요구에서 데이터 모델/전달 구조로 이어지는 설계 경험**을 얻었다. ERD나 DTO가 실제 백엔드 구현에 반영됐다는 기록, 테이블 수·DTO 수·성능 수치는 없어 언급하지 않는다.

## 복원의 핵심 교훈

이 경험의 가장 설득력 있는 설명은 **“병원 고객정보·담당자·데모·초음파 기기·VOC를 다루는 CRM의 Figma 화면에서 입력·조회·저장 요구를 해석하고, 이를 기능 명세·Jira 작업·ERD·SQL·DTO 설계로 연결했다”**이다.

다만 위 세 사례는 **각기 독립된 문제 해결 사건 세 건이 확인됐다는 뜻이 아니라, 한 현장실습의 연속된 업무를 설명 가능하도록 단계별로 나눈 것**이다. 아직 판단의 정확한 근거·현장에서 받은 피드백·변경 이전/이후 비교는 회고로도 복원되지 않았다.

## 이력서용 문구 (기억 기반, 검증 범위에 한정)

> **Beamworks 현장실습 (2026.01, 약 4주)** — 병원을 고객으로 하여 **병원 정보·병원 내 담당자·데모·초음파 기기·고객의 소리(VOC)를 관리하는 사내 CRM DealFlow**의 설계 업무를 경험했습니다. **Figma 화면의 입력·조회·저장 데이터 요구를 분석**하고 Jira Epic/Story/Task 단위의 업무 구조화 및 **ERD·DB 테이블·SQL·DTO 초안 작성**에 참여했습니다. 업무 대상은 의료영상 모델 개발이 아닌 **고객관리 서비스의 요구사항·데이터 설계**였습니다.

**자소서·면접 활용 방향:** 화면/업무 요구를 개발 가능한 세부 단위로 변환한 경험; 데이터 흐름·DB 설계 기본기; 사내 개발 협업 도구에 대한 적응 경험. **프로젝트 오너, 단독 백엔드 구현, 배포 성과, 수치화된 개선 효과로 과장하지 않는다.**

## 다음 회고에서 채우면 좋은 구체성

1. **개인 담당 범위:** 병원 / 병원 내 담당자 / 데모 / 초음파 기기 / VOC 중 **어느 화면이나 데이터 영역의 명세·ERD·SQL·DTO를 직접 작성**했는지.
2. **가장 고민했던 설계 결정 하나:** 어떤 데이터를 테이블로 분리하거나 어떤 화면 값의 입력/조회/저장 범위를 결정했는지.
3. **SQL·DTO의 실제 수준:** 테이블 생성문(DDL)이었는지 조회 SQL까지 썼는지, DTO가 어떤 언어/프레임워크의 스키마였는지.
4. **동료 피드백이나 결과:** 리뷰·수정 요청·완료/전달 여부. 없으면 '설계 경험'으로 유지.
5. **업무 프로세스 한 가지:** 데모 관리나 VOC 관리 중 실제로 기억나는 입력→상태 변경→조회 흐름과 팀 리뷰 피드백. 현재 구체적 상태나 처리 규칙은 미확정.

**중요:** 추가 회고를 받기 전까지 미확정 내용을 '그럴듯한 경험'으로 채우지 않는다. 이 문서는 현재 기억에 근거한 **초안**이며, 사실 확인이 되면 해당 항목별로 업데이트한다.
