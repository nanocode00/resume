# Beamworks — 병원 고객관리 플랫폼 DealFlow 현장실습

> **2026-10-29 기억 기반 복원(v0.3), 원본 산출물 미보유.** 기존 이력서/경험 문서와 2026-10-29의 본인 직접 회고로 작성했다. 당시 회사의 Figma·Jira·ERD·SQL·DTO·코드·검토 기록은 확보하지 못했으므로 **실제로 수행한 개인 업무**와 **최종 운영 반영 여부·세부 설계 수치**를 구분한다. [기억 기반 증거 원장](beamworks-memory-ledger.md) 참조.

## 한 줄 요약

**2026-01-01~01-28 약 4주간 의료기기 회사 Beamworks의 사내 병원 고객관리(CRM) 플랫폼 DealFlow에서, 디자이너가 Figma로 제작한 제품 전체의 목업 UI를 분석해 필요한 데이터 구조를 도출하고 ERD → SQL → DTO까지 직접 작성했다. 해당 설계 업무는 Jira로 관리했다.**

### 프로젝트와 개인 업무의 구분

- **프로젝트:** DealFlow는 병원을 고객으로 하는 의료기기 회사의 사내 CRM이다. **병원 정보, 병원 내 담당자, 데모, 초음파 기기, 고객의 소리(VOC)**를 관리하도록 구성되어 있었다.
- **직접 맡은 범위(본인 2026-10-29 회고):** **제품 전체**의 디자이너 Figma 목업 UI를 데이터 관점으로 분석하고 필요한 데이터 구조를 설계. **ERD → SQL → DTO를 작성**했으며, **Jira로 자신의 진행 작업을 관리**했다. 기존 기록에는 draw.io 기반 ERD와 Jira Epic/Story/Task 구조도 남아 있다.
- **업무의 성격:** UI 디자인을 만든 것은 **디자이너**이고, 본인 역할은 **디자인된 UI의 기능과 정보 요구를 백엔드 설계 산출물로 전환하는 작업**이다. 제품 전체를 대상으로 **설계했다**는 말은 모든 API·프런트엔드·배포 시스템을 단독 **구현했다**는 뜻이 아니다.
- **현장 정보:** Git/Jira/Bitbucket 교육·OJT와 2026-01-19 OJT 관련 메모가 있다. 구체적인 OJT 내용은 별도 증빙이 없다.
- **구체 수치 미확정:** ERD 테이블·관계 수, SQL 구문 종류, DTO 언어·클래스 수, Jira 티켓 수, 리뷰·승인 여부, 본인의 산출물이 운영 DB/API에 적용됐는지는 확인되지 않았다.

## DealFlow 관리 정보

| 영역 | 본인 회고에서 확인한 플랫폼 기능 범위 | 단정하지 않을 것 |
|---|---|---|
| **병원 정보** | 고객 병원 관련 정보 관리 | 병원 속성·키 및 직접 작성한 테이블 수 |
| **병원 내 담당자** | 병원 소속 담당자 정보 관리 | 담당자의 직책·연락처 등 특정 필드, 실제 FK |
| **데모 정보** | 데모 관련 정보 관리 | 예약/완료/반납 등의 구체 상태나 프로세스 |
| **초음파 기기 정보** | 초음파 장비 정보 관리 | 제품 모델·개별 장비 식별·이력 필드 |
| **VOC** | 고객의 소리 관리 체계 | 접수→처리→종결 등의 실제 워크플로 규칙 |

**개인 담당 범위는 제품 전체의 목업 기반 데이터 구조 설계**라는 점까지 이번에 회고로 확인했다. 그러나 위 다섯 영역이 각각 특정 테이블 한 개·DTO 한 개였다는 뜻도 아니고, 제품의 모든 런타임 기능을 직접 개발했다는 뜻도 아니다.

## 대표 경험 — Figma 목업을 데이터 설계 산출물로 전환

### 상황
빔웍스의 사내 CRM DealFlow는 병원, 병원 내 담당자, 데모, 초음파 기기, VOC 등 서로 다른 정보를 관리하는 제품이었다. **디자이너가 Figma로 설계한 제품 전체 목업 UI**를 기반으로 데이터 구조를 구체화하는 설계 업무를 맡았다.

### 문제
**Figma의 시각적 목업 자체만으로는 데이터 저장 구조, 엔터티 간 관계, 코드로 전달할 데이터의 형태가 완성되지 않는다.** UI에서 다루는 항목들을 개발자가 사용할 수 있는 명시적인 데이터 구조와 전달 형식으로 바꿔야 했다. 이 내용은 **수행 업무에서 도출한 설계 과제**이며, 당시 실제로 발생한 데이터 오류나 팀 간 갈등을 뜻하지 않는다.

### 판단
목업에서 표현되는 정보와 기능을 먼저 읽고 **어떤 데이터가 필요하며 입력·조회·저장되는지**를 파악한 다음, **데이터 간 관계 → DB 구조를 표현하는 SQL → DTO 형태의 데이터 전달 구조**로 구체화하는 순서를 적용했다. 정확한 개별 정규화/키 설계 의사결정은 아직 복원되지 않았다.

### 조치
1. **Figma 분석:** 디자이너가 제작한 제품 **전체**의 목업 화면을 확인하고 기능·필드와 요구 데이터 구조를 분석했다.
2. **ERD 작성:** 분석한 데이터와 관계를 **draw.io 기반 ERD**로 정리했다는 기존 회고가 있다.
3. **SQL 작성:** 설계된 데이터 구조를 표현하는 SQL을 작성했다. DDL/조회 SQL 여부와 실제 사용하는 DBMS는 미확인이다.
4. **DTO 작성:** 데이터 전달 구조를 나타낼 DTO를 작성했다. 특정 언어/프레임워크 및 실제 API 반영은 미확인이다.
5. **Jira 관리:** 이 일련의 작업 진행을 **Jira로 관리**했다. 기존 기록에는 **Epic/Story/Task**라는 분해 체계가 있으나 정확한 생성·완료 건수와 운용 규칙은 남아 있지 않다.

### 결과
**제품 전체를 대상으로 한 Figma UI의 요구 데이터 분석과 ERD·SQL·DTO 작성 작업**을 수행했다. 제품의 관리 정보를 저장·전달하기 위한 설계 작업을 경험했고, 그 진행 과정을 Jira에서 관리했다는 점을 개인 기여로 설명할 수 있다.

다만 **설계 산출물 작성**과 **해당 설계가 제품에 병합·배포되어 운영되었다는 사실**은 별개다. 원본 산출물 및 리뷰 기록이 없으므로 성과 수치, 구현 완료·실서비스 적용·성능 향상으로 확대하지 않는다.

## Jira 협업·온보딩 경험의 위치

Jira는 독립된 프로젝트 관리 제도를 도입한 성과가 아니라 **Figma 분석 및 ERD→SQL→DTO 작성을 진행하는 과정에서 실제 사용한 작업 관리 도구**였다. Git·Bitbucket은 당시 교육·온보딩 경험이 있었던 도구로 기록하며, 소스 병합이나 CI/CD 구축 실적으로 확대하지 않는다.

## 이력서용 표현

> **Beamworks 현장실습 (2026.01, 약 4주)** — 병원 정보·병원 내 담당자·데모·초음파 기기·VOC를 관리하는 사내 **CRM DealFlow**에서, **디자이너의 Figma 목업 UI를 제품 전체 범위로 분석해 필요한 데이터 구조를 도출**하고 **ERD(draw.io) → SQL → DTO**를 직접 작성했습니다. 설계 작업은 **Jira Epic/Story/Task** 체계를 활용해 관리했습니다.

**활용 직무/역량:** Backend/Data 설계, UI 요구사항과 DB 모델의 연결, 실무 협업·업무 구조화, B2B 의료기기 고객관리 도메인의 이해.

**면접 시 피할 과장:** 디자이너의 UI 자체를 제작, CRM 전체 백엔드 API 개발, 모든 DB 테이블과 DTO의 최종 운영 반영, VOC 처리 자동화 구현, 제품 출시/의료영상 AI 개발, 처리속도·생산성 개선 수치.

## 남아 있는 회고 보강점

**직접 담당한 범위와 일의 순서는 충분히 확인됐다.** 선택적으로 세부성을 더하려면 다음을 회고할 수 있다.

1. **대표 관계 설계 결정:** 병원–담당자 / 병원–데모 / 기기 / VOC 중 데이터 관계를 어떻게 표현했는지.
2. **SQL·DTO의 구체 형태:** DDL인지 조회문도 있었는지, DTO 언어·파일 구조가 무엇인지.
3. **Jira와 검토:** 진행 상태를 어떻게 관리했고, 작성한 ERD·SQL·DTO에 대한 동료 피드백이나 전달·승인 과정이 있었는지.

원본이 없다면 위 사항을 억지로 채우지 않고 **현재의 기억 기반 설명을 유지**한다.
