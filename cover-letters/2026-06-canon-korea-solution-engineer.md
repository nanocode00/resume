## 1. 지원자님은 어떤 분이신가요? 지원자님의 현재 모습에 영향을 끼친 경험이나 상황이 있다면 알려 주세요. (삶의 가치관, 성격, 성향 등) (700자)

문제를 만나면 주어진 도구를 그대로 쓰기보다, 왜 불편한지 살피고 사용 환경에 맞게 바꿀 방법을 찾는 사람입니다. 이런 성향은 문제를 발견하고 직접 고쳐본 경험들이 쌓이며 만들어졌습니다.

고등학생 때 아두이노를 배운 뒤, 방과후 동아리에서 브레드보드와 부품으로 아두이노 보드를 만들어보았습니다. 이후 같은 회로를 만능기판에 옮겼지만, 기판 아래 전선이 복잡해 수정과 확인이 어려웠습니다. 원인이 배선 방식에 있다고 생각했고, 더 깔끔한 방법을 찾다 PCB를 알게 되었습니다. 이후 책으로 설계 방법을 공부해 제작 파일을 만들고 해외 주문까지 해보았습니다.

이때의 PCB 제작 경험은 복학 전 참여한 Paperware 프로젝트에서 문제 해결의 밑거름이 되었습니다. Paperware는 교육용 키트로, 카드보드 위 구리테이프 회로에 클립형 모듈을 끼워 사용하는 방식이었습니다. 네오픽셀을 쓰려면 시중 모듈에 납땜 등 추가 작업이 필요했고, 카드보드 회로와 맞닿기도 어려웠습니다. 그래서 뒷면 접점을 크게 만들어 구리테이프와 연결되는 전용 모듈을 설계했고, 시제품을 주문해 카드보드 무드등에 활용했습니다.

이 과정에서 문제 해결은 새 기능을 더하는 일만이 아니라, 사용 환경에 맞지 않는 부분을 발견하고 고치는 일이라는 점을 배웠습니다. 캐논코리아에서도 현장 고객의 문제를 이해하고, 그 환경에 맞는 솔루션을 제안하고 구현하는 사람이 되고 싶습니다.

## 2. 실패와 성공 여부를 떠나, 스스로 목표를 세워 도전해 본 경험과 그 과정에서 배운 점을 구체적으로 작성해 주세요. (700자)

시각장애인도 코딩의 흐름을 직접 체험할 수 있는 앱을 만들겠다는 목표로 허밍블럭스 프로젝트에 도전했습니다. 전국 장애 비장애 대학생 창업경진대회를 계기로 시작했지만, 아이디어에서 멈추지 않고 출시 가능한 앱으로 만드는 것을 목표로 삼았습니다.

허밍블럭스는 명령 블록을 순서대로 놓고 사진을 찍으면, 앱이 블록을 인식해 순서와 기능을 해석하고 결과를 음악으로 들려주는 코딩교육용 앱입니다. 처음에는 블록을 정확히 인식시키면 목표에 가까워질 것이라고 생각했습니다. 그러나 개발을 시작하자 과제는 하나가 아니었습니다. 카메라 입력, 인식 결과의 중복 제거와 순서 정리, 블록 정보를 실행 데이터로 바꾸는 작업, 음악으로 결과를 전달하는 흐름까지 나누어 풀어야 했습니다.

그래서 목표를 기능 단위로 나누었습니다. 안드로이드 개발을 익혀 촬영과 화면 흐름을 만들고, YOLO 학습용 데이터를 라벨링하며 인식 기능을 준비했습니다. 이후 모델 출력값을 앱에서 처리할 수 있도록 블록 타입과 실행 순서를 정리했고, 화면과 음악을 연결했습니다. 휴학을 선택해 개발을 이어갔고, 착수 약 1년 8개월 후 출시했습니다.

이 경험을 통해 도전은 큰 목표를 한 번에 해결하는 일이 아니라, 막연한 문제를 작은 단위로 나누고 하나씩 검증해 완성도를 쌓는 과정임을 배웠습니다. 캐논코리아에서도 고객사의 복잡한 요구사항을 구조적으로 파악하고, 끝까지 결과물로 연결하겠습니다.

## 3. 혼자서는 해내기 어려운 일을 다른 사람들과 협력하여 성취한 경험에 대해 기술해 주세요. 그 과정에서 어려웠던 점은 무엇이었고, 이를 통해 무엇을 배우셨나요? (700자)

webOS 스마트 화분 프로젝트는 구성 요소가 많아 혼자 해결하기 어려운 협업 경험이었습니다. 식물 상태를 센서로 확인하고 물 공급 동작을 수행한 뒤, webOS 화면과 외부 웹앱에서 상태를 확인하는 시스템이었기 때문에 하드웨어, UI, 서버 연동을 모두 혼자 맡기에는 시간과 경험이 부족했습니다.

화분 단말은 webOS OSE를 올린 라즈베리파이가 아두이노에 명령을 보내 센서값을 읽거나 액추에이터를 동작시키는 구조였습니다. webOS 안에서는 UI, 하드웨어 제어, 서버 연동을 이어주는 JS Service가 필요했고, 외부 React 웹앱은 AWS를 통해 화분과 연결되어야 했습니다. 하드웨어 제어는 직접 구현할 수 있었지만, UI와 JS Service, AWS 연동은 팀원과 역할을 나누어야 했습니다.

다른 팀원은 React UI와 외부 웹앱, AWS 연동, JS Service 구성을 맡았고, 저는 하드웨어 제어와 센서값 전달 방식을 정리했습니다. 어려웠던 점은 각 부분이 어떤 데이터 형식과 기준으로 만나야 하는지 맞추는 일이었습니다. 센서값 이름과 범위, 액추에이터 상태가 어긋나면 기능이 동작해도 사용자가 이해하기 어려웠습니다.

이를 줄이기 위해 전달할 값과 상태 기준을 공유했고, UI와 웹앱에서 필요한 정보가 생기면 코드를 수정하며 맞춰갔습니다. 이 경험을 통해 협업은 맡은 일을 끝내는 데 그치지 않고, 상대가 활용할 수 있는 형태로 결과물을 정리하는 과정임을 배웠습니다.

## 4. 지원하신 직무를 수행할 수 있는 역량을 갖추기 위해 어떠한 준비와 노력을 하셨는지 구체적인 사례를 중심으로 설명해 주세요. (700자)

솔루션엔지니어 직무에는 고객 요구를 기술적으로 해석하고, 시스템에 맞게 구현한 뒤 안정적으로 동작하는지 확인하는 역량이 필요하다고 생각합니다. 이를 위해 요구사항을 개발 단위로 바꾸는 경험과 동작을 끝까지 검증하는 경험을 쌓았습니다.

빔웍스 현장실습에서는 Figma 화면을 바탕으로 요구사항을 정리하고 Jira의 Epic, Story, Task로 나누어 관리했습니다. 처음에는 화면 항목이 어떤 데이터로 저장되고 전달되어야 하는지 판단하기 어려웠습니다. 그래서 입력값, 조회 항목, 저장 항목을 나누고, 데이터 구조 설계부터 SQL과 DTO 구현까지 연결했습니다. 요구사항은 문장으로 이해하는 데서 끝나지 않고 개발 가능한 구조로 바뀌어야 한다는 점을 배웠습니다.

기술적 검증 역량은 논리회로설계 프로젝트로 길렀습니다. Verilog 단일 사이클 CPU에서는 예외 처리와 복귀 흐름을 구현하며 중간 신호를 따라 오류 원인을 확인했고, CNN 가속기 프로젝트에서는 RTL과 Netlist 결과를 비교해 합성 이후에도 동작이 유지되는지 검증했습니다. 오류가 생기면 전체를 추측하지 않고 입력, 출력, 중간 결과를 기준으로 원인을 좁히는 방식을 익혔습니다.

이 방식은 솔루션 장애 대응에도 필요하다고 생각합니다. 캐논코리아에서도 고객 요청을 해석하고, 운영 중 문제 원인을 체계적으로 확인해 안정적으로 동작하는 솔루션을 만드는 데 기여하겠습니다.
