## 1. 직무 전문성 — 지원 분야 및 직무 역량과 관련된 프로젝트/공모전/논문/연구/학습/활동/경험 등을 작성해 주세요. (2000자)

[기간] 2025.03 ~ 2025.06
[경험] Logisim 단일 사이클 CPU의 Verilog RTL 구현
[역할] 개인 프로젝트 / CPU 모듈 구현 및 동작 검증

논리회로설계 수업에서 Logisim으로 구현된 단일 사이클 CPU를 Verilog로 옮기며 하드웨어 동작을 확인했습니다. Control, ALU, Register File, Memory, CP0를 구성하고 기존 프로그램과 실행 결과가 일치하는지를 기준으로 검증했습니다. 일반 명령은 동일하게 동작했지만 버튼 입력으로 예외 처리 경로에 진입하면 결과가 달라졌습니다. ALU 입력과 제어값, EPC 저장 시점과 PC 흐름을 파형으로 추적한 결과 ERET 복귀 과정에서 리셋 신호가 적용되는 시점이 Logisim과 다르게 동작하는 구간까지 원인을 좁혔습니다. 차이를 완전히 해소하지는 못했지만 같은 논리 구조라도 신호가 적용되는 시점과 구현 방식에 따라 결과가 달라질 수 있음을 확인했습니다. 이후 예상 출력만 비교하기보다 내부 신호와 상태 변화를 함께 확인하는 방식으로 검증했습니다.

[기간] 2025.03 ~ 2025.06
[경험] CNN Accelerator RTL to Netlist 구현 및 검증
[역할] 팀 프로젝트 / 양자화 실험, RTL 검증, OpenROAD 합성 및 timing, power 분석

기존 2단 CNN Verilog 구현을 바탕으로 소프트웨어 모델과 하드웨어 구현의 결과를 검증했습니다. PyTorch에서 양자화를 별도로 실험하고 weight, bias와 계층별 출력값을 정수 형태로 추출해 Verilog 구현의 연산 결과와 비교했습니다. MNIST 1,000장을 연속 입력하는 테스트벤치에서는 RTL 분류 정확도 96%를 확인했습니다. 이후 OpenROAD ASAP7 환경에서 RTL을 합성해 Netlist를 생성하고 배치 결과와 timing, power report를 확인했습니다. RTL 시뮬레이션에서는 정상적으로 분류 결과가 출력됐지만 합성한 Netlist를 시뮬레이션하자 출력이 계속 0으로 나타났습니다. 동일한 테스트벤치 입력을 사용해 RTL과 Netlist 시뮬레이션 결과를 비교했습니다. **합성 결과가 수십만 줄 규모로 복잡해져 파형만으로 원인을 추적하기 어려웠고, 프로젝트 기간 안에 원인을 특정하지 못했습니다.** 이 때문에 Netlist의 정확도와 합성 전후 결과 일치 여부까지는 검증하지 못했습니다.

[기간] 2024.03 ~ 2024.11
[경험] webOS OSE 기반 스마트 화분 시스템 개발
[역할] 팀 프로젝트 / Arduino 센서 및 액추에이터 제어, I2C 인터페이스 설계, webOS 연동

LG전자 산학연계 프로젝트에서 Raspberry Pi의 webOS OSE와 Arduino를 활용한 스마트 화분을 개발했습니다. Arduino에서 온습도, 조도, 수위, 토양수분 센서를 읽고 급수 펌프와 NeoPixel을 제어하는 로직을 구현했습니다. 장치 기능을 webOS에서 사용할 수 있도록 I2C 통신 규칙도 직접 정의했습니다. mode 0은 NeoPixel 밝기 제어, mode 1은 펌프 켜기와 끄기, mode 2는 센서 조회로 구분했습니다. webOS에서 mode 0을 선택한 뒤 0~100의 밝기 값을 보내면 Arduino가 0~255 범위로 변환해 24개 LED가 있는 NeoPixel에 적용하고, mode 1에서는 0과 1로 펌프를 제어하도록 구현했습니다. mode 2에서는 DHT의 온습도 4바이트, 조도 2바이트, 수위 2바이트, 토양수분 2바이트를 합쳐 총 10바이트를 한 번에 반환하도록 구성했습니다. webOS에서는 같은 규칙으로 명령을 전송하고 반환 데이터를 실제 센서값으로 변환하는 제어 코드를 작성해 담당 팀원에게 전달했습니다. 이 명령 규칙을 기준으로 Arduino와 webOS의 구현을 연결했습니다. React 기반 화면 일부도 구현해 센서 상태와 장치 제어 기능을 확인할 수 있도록 했습니다. 이후 프로젝트를 임베디드 소프트웨어 경진대회 webOS 부문으로 발전시켜 출품하고 입선했습니다.

## 2. AI 기반 문제 해결 경험 — AI를 활용한 프로젝트/공모전/논문/연구/문제 해결 경험 등을 작성해 주세요. (2000자)

[기간] 2026.06 ~ 현재
[경험] 고령 사용자를 위한 음성 중심 키오스크 말로(Mallo) 개발
[역할] 팀장 / TTS 파인튜닝, AI 모델 비교, 경쟁사 분석 및 UI 개선 방향 수립

ESTsoft AI Human 과정의 팀 프로젝트에서 고령 사용자의 키오스크 주문 부담을 줄이기 위한 음성 중심 키오스크 말로(Mallo)를 개발하고 있습니다. AI Hub 친절체 음성 데이터로 MeloTTS와 Qwen3-TTS를 파인튜닝한 뒤 생성 샘플을 직접 확인했습니다. 처음 파인튜닝한 후 두 모델 모두 일부 문장에서 외계어처럼 들리는 문제가 있었습니다. 이상 출력을 발견한 뒤 AI 코딩 에이전트에 원인 분석과 수정을 지시하고, 수정 결과를 다시 청취해 정상 여부를 검증했습니다. 이 과정에서 토큰 처리와 관련된 학습 설정을 보완한 뒤 정상적인 한국어 음성이 생성되는 것을 확인했습니다.

수정 후 MeloTTS는 학습 데이터의 음색 방향으로 변화했지만 체감되는 감정 표현은 크지 않았습니다. 반면 Qwen3-TTS는 친절체 학습 데이터와 더 유사한 억양과 분위기로 들렸습니다. 같은 20개 주문 문장을 GPU에서 측정했을 때 Baseline 평균 생성 지연은 MeloTTS 약 0.20초, Qwen3-TTS 약 6.91초였고, 파인튜닝 모델에서도 MeloTTS는 약 0.2초, Qwen3-TTS는 수 초 수준이었습니다. 청취 품질은 Qwen3-TTS가 더 좋게 느껴졌지만 음성 주문 데모에서는 사용자가 기다리는 시간을 줄이는 것이 더 중요하다고 판단해 MeloTTS를 적용하기로 결정했습니다.

TTS 생성 시간과 전체 서비스 응답시간도 구분했습니다. TTS 성능은 반복 합성 결과의 평균, p95, RTF로 비교하고, 전체 음성 주문은 발화 종료 이후 STT, NLU, 주문 처리, TTS와 실제 재생까지 포함하는 별도의 E2E 문제로 보았습니다. 발화 종료부터 첫 음성 재생까지 목표 1.2초, 요구사항 1.5초의 검증 기준을 정했으며, 아직 실제 E2E 측정을 완료하지 않았기 때문에 TTS 벤치마크만으로 목표를 달성했다고 판단하지 않았습니다. 기준을 넘으면 전체 모델을 바꾸기보다 구간별 병목을 먼저 확인하도록 방향을 정했습니다.

경쟁사 분석 후에는 음성 입력 상태, 실시간 자막, 발화 종료 후 빠른 진행이 중요하다고 판단해 UI 변경 방향을 정했습니다. 결과를 반복 확인하며 듣는 중과 처리 중 상태, 자막, 주문 확인 정보가 명확히 드러나도록 개선했습니다. 화면 요소의 우선순위와 상태 전환 흐름도 함께 조정했습니다. 최근에는 NLU 파인튜닝 지연을 확인해 기존 담당자와 함께 학습을 진행하고, 다른 팀원은 NLU를 제외한 E2E 연결을 먼저 검증하도록 역할을 재배분했습니다. 한 기능의 지연으로 전체 통합 검증이 멈추지 않도록 병렬로 진행 가능한 작업을 나눴습니다.

[기간] 2022.03 ~ 2025.01
[경험] 시각장애인 코딩교육 제품 HummingBlocks 개발
[역할] Android 앱 개발 및 AI 추론 연동

HummingBlocks에서는 YOLO가 검출한 실물 블록의 종류와 좌표를 받아 배치를 판단하고 음악 실행 순서로 변환하는 후처리와 22가지 예외 처리를 구현했습니다. 예외 상황이 발생하면 사용자가 원인을 알 수 있도록 화면에 안내 메시지도 표시했습니다. PyTorch 모델을 Chaquopy로 실행하는 방식은 모바일 추론에 약 9.1초가 걸려 TFLite를 적용해 Java에서 직접 추론하는 방식을 시험했습니다. 그 결과 약 5.4초까지 줄였지만 인식 정확도가 낮아졌습니다.

블록을 잘못 인식하면 사용자가 구성한 음악 자체가 달라지기 때문에 속도보다 정확성이 중요했습니다. 실제 제품에는 기존 PyTorch와 Chaquopy 방식을 유지했고, 야외와 노을 환경에서 인식이 잘되지 않는 조건도 AI 담당자에게 공유했습니다.

두 경험에서는 서로 다른 기준으로 기술을 선택했습니다. Mallo에서는 음질보다 응답성을, HummingBlocks에서는 속도보다 정확성을 우선했습니다. AI 모델의 성능 수치 하나만 따르기보다 실제 출력과 사용 환경을 확인하고, 서비스 목적에 맞는 기준으로 기술을 선택해야 한다는 점을 배웠습니다. 앞으로도 시스템 제약과 사용자 경험을 함께 검토하고, 측정과 검증 결과를 근거로 기술적 대안을 선택하겠습니다.
