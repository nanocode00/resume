## 1. 유진테크에 지원하게 된 동기를 기술하여 주세요. (1400바이트)

유진테크 SW개발 직무에 지원한 이유는 소프트웨어가 실제 설비를 움직이고, 그 동작을 안정적으로 이어지게 만드는 일에 도전하고 싶기 때문입니다. 이 직무는 순서에 맞춰 장치가 움직이도록 만들고, 기능을 더하며, 문제가 생기면 원인을 찾아 고치는 일이라고 이해했습니다. 코드가 화면 안에서 끝나지 않고 장치 반응과 작업 흐름으로 이어진다는 점이 매력적이었습니다.

이 관심은 고등학생 시절부터 이어온 제작 경험에서 시작되었습니다. Arduino와 Raspberry Pi, micro:bit로 센서와 액추에이터를 다루며 모터와 LED를 제어했습니다. 이때 장치의 반응을 보며 수정하는 태도를 익혔습니다. 네모감성의 페이퍼웨어 프로젝트에서는 micro:bit를 카드보드 회로에 연결하는 교육용 키트를 만들고, 필요한 네오픽셀 모듈을 PCB로 설계해 카드보드 무드등에 활용했습니다.

LG 산학연계 종합설계에서는 webOS 기반 스마트 화분 프로젝트에서 하드웨어와 React UI 일부를 맡았습니다. 센서와 구동부를 포함한 장치 구성을 확인하고, 화면에서 식물 상태를 확인하는 흐름을 고민했습니다. 하드웨어 상태가 화면에 표시되고 사용자 조작이 장치 동작으로 이어지려면, 기능별 연결 관계와 상태 변화를 맞춰야 한다는 점을 경험했습니다.

유진테크에서도 장비의 상태를 파악하고, 정해진 순서에 맞게 동작하도록 만드는 SW를 개발하고 싶습니다. 작은 상태 변화나 제어 흐름의 어긋남도 장비 동작에 영향을 줄 수 있는 만큼, 하드웨어 동작을 이해하며 기능을 구현하겠습니다. 문제가 발생했을 때는 현상을 재현하고 조건을 하나씩 확인하며 원인을 좁혀, 안정적인 장비 운영에 기여하겠습니다.

## 2. 지원직무를 성공적으로 수행할 수 있다고 생각하는 이유와 이를 위해 어떤 준비를 해 왔는지에 대하여 구체적으로 기술하여 주세요. (1400바이트)

지원직무를 성공적으로 수행할 수 있다고 생각하는 이유는 SW와 하드웨어 사이의 동작 흐름을 함께 이해하려고 준비해 왔기 때문입니다. 컴퓨터학부에서 운영체제, 데이터베이스, 컴퓨터구조, 컴퓨터망을 배우며 SW 기초를 쌓았고, 전자공학 부전공을 통해 논리회로, 회로이론, 전자소자 등을 공부하며 장치 동작의 기반도 넓혔습니다.

그중 논리회로설계 수업은 장비 SW와 가장 가까운 준비 경험이었습니다. Verilog로 싱글사이클 CPU를 구현하며 명령어가 제어 신호, ALU, 레지스터, 메모리를 거쳐 결과로 이어지는 흐름을 직접 연결했습니다. CNN 가속기 과제에서는 PyTorch 모델의 가중치와 중간 출력값을 정수화해 Verilog 구현에서 재현하고, RTL과 합성 Netlist 결과를 비교했습니다. 이를 통해 기능을 만드는 것뿐 아니라 같은 입력에서 같은 결과가 나오는지 확인하는 검증 태도를 익혔습니다.

마이크로프로세서 수업에서는 ARM 명령어 구조를 배우며 컴퓨터구조 과목에서 배운 내용을 연결했습니다. 컴퓨터구조에서 명령어 실행, 레지스터, 메모리 접근을 배웠다면, 마이크로프로세서에서는 실제 ARM 명령어가 어떤 형식으로 값을 읽고 쓰며 분기와 연산을 수행하는지 확인했습니다. 코드 한 줄이 내부에서는 레지스터 선택, 데이터 이동, 조건 판단, 메모리 접근으로 나뉘어 실행된다는 점을 이해할 수 있었습니다.

유진테크 장비 SW에서도 장비 상태를 읽고 정해진 순서에 맞게 동작시키는 흐름을 정확히 이해하는 힘이 필요하다고 생각합니다. 배운 내용을 바탕으로 기능 구현 후 동작을 확인하고, 문제가 생기면 조건을 나누어 원인을 좁혀 안정적인 장비 운영에 기여하겠습니다.

## 3. 본인 성격의 장점과 단점을 지원분야와 연관지어 각각 기술하여 주세요. (1400바이트)

장점은 문제가 생겼을 때 현상만 보고 넘기지 않고, 조건을 나누어 원인을 확인하는 성격입니다. 장비 SW개발에서는 장비가 정해진 순서대로 동작하는지, 어느 조건에서 문제가 생기는지 확인하는 태도가 중요하다고 생각합니다. 논리회로설계 수업에서 Verilog로 싱글사이클 CPU와 CNN 가속기 과제를 수행하며 이 장점을 기를 수 있었습니다.

CPU 프로젝트에서는 명령어 실행 결과가 예상과 다를 때 ModelSim 파형을 보며 PC 변화, 제어 신호, 레지스터 입력, 메모리 접근을 단계별로 확인했습니다. 처음에는 결과값만 보려 했지만, 신호가 흐르는 순서를 따라가야 원인을 찾을 수 있다는 점을 배웠습니다. CNN 가속기 과제에서도 PyTorch 모델 값을 Verilog 구현에 맞추고, 같은 입력에 대해 RTL과 합성 Netlist 결과가 일치하는지 비교했습니다. 이를 통해 기능 구현 후에도 동작을 끝까지 확인하는 습관을 길렀습니다.

단점은 더 나은 방법을 찾으려다 적용 시점과 범위를 늦게 정할 때가 있다는 점입니다. 허밍블럭스 앱을 운영하며 성능이나 안정성을 높일 수 있는 방법을 계속 비교한 적이 있습니다. 하지만 업데이트 일정이 가까운 상황에서는 새로운 개선을 무리하게 넣기보다, 적용 효과와 검증 범위를 먼저 정해야 한다는 점을 느꼈습니다.

이후에는 개선안을 볼 때 우선순위, 일정, 검증 가능성을 함께 따지려 노력하고 있습니다. 장비 SW에서도 좋은 기능을 추가하는 것만큼 안정적으로 반영하는 과정이 중요하다고 생각합니다. 장점인 원인 추적 태도는 살리고, 단점은 기준을 세워 보완하며 작은 오류도 확인하는 개발자로 유진테크 장비의 안정적인 동작에 기여하겠습니다.
