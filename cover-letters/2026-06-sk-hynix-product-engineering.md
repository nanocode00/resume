## 경험기술서 1. AI 활용 경험 기술 (3000자)

### [경험 1] AI 기반 시각장애인 코딩 교육 앱 ‘허밍블럭스’ 개발

허밍블럭스는 시각장애인이 실물 코딩 블록을 조립한 뒤 스마트폰으로 촬영하면, 인공지능이 블록을 인식하여 조립 순서에 맞는 음악을 실행하는 교육용 애플리케이션입니다. 저는 약 1년간 개발에 참여하며 AI 모델의 인식 결과를 Android 애플리케이션의 실제 기능으로 연결하는 역할을 담당했습니다.

애플리케이션은 이미지 촬영, YOLO 기반 블록 인식, 결과 후처리, 음악 실행의 순서로 동작했습니다. 모델은 블록의 종류, 신뢰도, 바운딩 박스 정보를 출력했지만, 이를 그대로 사용하면 하나의 블록이 중복 인식되거나 촬영 각도에 따라 실행 순서가 달라지는 문제가 있었습니다.

이를 해결하기 위해 모델의 출력값을 클래스, 신뢰도, 위치 정보로 구성된 리스트 형태로 전달받아 후처리 로직을 구현했습니다. NMS 방식을 적용해 겹치는 바운딩 박스 가운데 신뢰도가 높은 결과만 남기고, 블록의 위치 관계를 기준으로 실행 순서를 정렬했습니다. 이후 블록 종류와 템포 등의 정보를 음악 실행 모듈에서 사용할 수 있는 데이터 구조로 변환했습니다. 이를 통해 단순한 객체 인식 결과가 사용자가 조립한 순서대로 동작하는 실행 명령으로 이어지도록 만들었습니다.

Python으로 구현된 PyTorch 기반 YOLO 모델을 Android에서 실행하기 위해 Chaquopy로 Java와 Python을 연동했습니다. 그러나 갤럭시 S9+에서 평균 처리 시간이 9.1초로 측정되어 속도 개선이 필요했습니다. 이에 모델을 TensorFlow Lite 형식으로 변환해 Java에서 직접 추론하는 방식을 구현하고 기존 방식과 비교했습니다.

TensorFlow Lite 적용 후 평균 처리 시간은 5.4초로 약 41% 단축됐지만, 인식 정확도는 기존 PyTorch 모델의 90%에서 57%로 떨어졌습니다. 허밍블럭스는 인식 결과가 곧바로 음악 실행으로 이어지는 교육용 앱이므로, 빠른 응답보다 사용자가 조립한 블록을 정확하게 판별하는 것이 더 중요하다고 판단했습니다. 이에 기존 Chaquopy 방식을 유지했습니다. 이 과정에서 하나의 성능 지표만으로 기술을 선택하지 않고, 제품의 목적과 사용자에게 미치는 영향을 기준으로 우선순위를 판단해야 한다는 점을 배웠습니다. 프로젝트는 Google Play 출시와 실제 제품 판매로 이어졌습니다.

### [경험 2] CNN과 Mamba를 활용한 암호화폐 호가 방향 예측

암호화폐 거래소의 호가 데이터를 활용해 일정 시간 이후의 가격 상승과 하락을 예측하는 프로젝트를 진행했습니다. 프로젝트는 4명의 팀원이 각자 다른 모델 방식을 선정해 구현하고, 최종적으로 모델별 예측 결과를 비교하는 방식으로 진행했습니다.

저는 호가창의 가격 단계별 주문량 관계와 연속적인 시간 변화를 함께 학습하기 위해 CNN과 Mamba를 결합한 모델을 선정했습니다. CNN으로 호가창 내 가격대별 국소 패턴을 추출하고, Mamba로 연속된 호가 흐름을 학습하도록 구성했습니다. 해당 모델에 필요한 데이터 전처리부터 입력 특성 구성, 모델 구현, 학습, 평가까지 전체 실험 과정을 수행했습니다. Binance와 Upbit의 호가 및 체결 데이터를 활용해 상대 가격, 정규화된 주문량, 매수·매도 불균형을 입력 특성으로 구성했습니다. 연속된 호가 데이터는 일정 길이의 시퀀스로 가공하고, 예측 시점의 가격 변동을 기준으로 상승과 하락 라벨을 생성했습니다.

입력 구간과 예측 시점을 조정하며 5초 후와 15초 후의 가격 방향을 예측했고, 15초 예측 모델에서 약 59.5%의 검증 정확도를 확인했습니다. 그러나 전체 정확도만으로는 특정 방향에 편향된 모델인지 판단하기 어렵다고 생각했습니다. 이에 혼동행렬을 통해 실제 상승과 하락을 각각 얼마나 정확하게 분류하는지 확인하고 예측 편향을 분석했습니다. 이후 모델의 예측이 실제 거래에서도 유효한지 확인하기 위해 거래 수수료를 반영한 백테스트를 진행했습니다.

검증 데이터에서는 일정 수준의 방향 예측 성능을 보였지만, 거래 비용을 적용하면 안정적인 수익을 확보하지 못했습니다. 이를 통해 분류 정확도만으로 모델의 활용 가능성을 판단해서는 안 되며, 실제 운영 환경의 비용과 제약까지 포함해 검증해야 한다는 점을 배웠습니다.

두 경험에서 AI 결과를 실제 기능과 운영 조건에 연결하고, 단일 지표가 아니라 제품 목적과 사용 환경을 기준으로 기술의 유효성을 판단했습니다. SK하이닉스의 Product Engineering 직무에서도 테스트 결과와 제품 특성을 함께 분석해 이상 원인을 좁히고, 실제 조건에서 신뢰할 수 있는 판단 기준을 만드는 데 기여하겠습니다.

## 경험기술서 2. 직무 경험 기술 (3000자)

### [2025.05 ~ 2025.06] Logisim 기반 단일 사이클 CPU의 Verilog 구현 및 검증

역할: 전체 모듈 구현, 테스트벤치·TCL 스크립트 작성, Logisim·ModelSim 결과 비교 및 오류 분석

논리회로설계 과목의 개인 과제로 MIPS 계열의 단일 사이클 CPU를 Verilog로 구현했습니다. GitHub에 공개된 Logisim 기반 single-cycle CPU를 기준 설계로 삼아 회로의 구성과 신호 흐름을 분석하고, 이를 Control, Opcode Decoder, ALU, Register File, Instruction Memory, Data Memory, Immediate Extender 등의 기능별 모듈로 나누어 구현한 뒤 상위 모듈에서 연결했습니다. 또한 Logisim 설계를 참고해 CP0 관련 제어 신호를 구현하고, 예외 발생 시 EPC에 복귀 주소를 저장한 뒤 예외 처리 주소로 이동하고 ERET 명령으로 기존 실행 흐름에 복귀하도록 구성했습니다.

모듈별 동작을 확인하기 위해 입력 조건과 테스트케이스를 포함한 테스트벤치를 작성했습니다. ModelSim에서는 테스트벤치를 실행하고 필요한 신호만 파형 창에서 확인할 수 있도록 TCL 스크립트도 구성했습니다. 예를 들어 ALU 검증 시 입력값과 제어 신호, 연산 결과와 상태 신호를 선별해 추가하고, 신호의 성격에 따라 16진수 또는 2진수로 표시한 뒤 100ns 동안 실행하도록 설정했습니다.

검증은 원본 Logisim 회로와 비교하는 방식으로 진행했습니다. 동일한 입력을 적용한 뒤 Logisim을 한 tick씩 진행하며 PC, 명령어, 제어 신호, ALU 입출력과 레지스터 값을 확인하고, ModelSim의 같은 시점에서 나타난 결과와 대조했습니다. 두 결과가 일치하지 않으면 최종 출력만 보고 코드를 수정하지 않고 신호가 최초로 달라지는 지점부터 데이터 경로를 역추적했습니다. 이 과정에서 ALU 입력 연결 순서가 뒤바뀐 문제, Opcode Decoder에서 ADDI와 ANDI 조건을 혼동해 ALUSrc와 RegWrite 신호가 잘못 생성된 문제, CP0 신호 연결 순서 오류를 찾아 수정했습니다.

다만 Logisim에서 래치 형태로 구성된 EPC는 설계를 참고해 Verilog로 구현했음에도 ModelSim에서 복귀 주소가 의도대로 저장되지 않았습니다. PC와 명령어, 예외 발생 신호, EPC의 입력과 출력을 시점별로 비교해 문제 범위를 EPC의 래치 동작과 신호 변화 시점으로 좁혔지만, 프로젝트 기간 내에 정확한 원인을 확정하고 완전히 해결하지는 못했습니다. 이를 통해 기존 회로를 HDL로 구현할 때는 논리 연결뿐 아니라 저장 소자의 동작 조건과 신호 변화 시점까지 고려해야 하며, 기준 모델과의 단계별 비교를 통해 최초 불일치 지점부터 원인을 좁혀야 한다는 점을 배웠습니다.

### [2025.06 ~ 2025.07] CNN RTL의 OpenROAD 합성 환경 구축 및 Netlist 검증

역할: Linux 실행 환경 및 저장소 구성, OpenROAD 설정 조정, 합성·Netlist 검증 주도

논리회로설계 과목의 팀 과제로 GitHub에 공개된 Verilog 기반 CNN 회로를 OpenROAD에서 합성하고, 가능한 범위에서 전력 소모를 줄이는 프로젝트를 수행했습니다. 팀원들은 양자화 등 전력 절감 방안을 조사했고, 저는 팀 내에서 Linux와 GitHub 사용 경험이 상대적으로 많았기 때문에 실행 환경 구축부터 저장소 관리, OpenROAD 실행과 오류 대응, 합성 결과 검증까지 전체 기술 작업을 주도했습니다.

먼저 전력 절감 방안 중 하나로 모델 양자화를 직접 시도했습니다. 관련 Python 코드를 Windows에서 실행하는 과정에서 일부 모듈의 호환성과 의존성 문제가 발생해 WSL로 전환했지만 문제를 완전히 해소하지 못했고, 최종적으로 Ubuntu 가상머신을 구축했습니다. Windows에서 WSL, Ubuntu VM으로 실행 환경을 단계적으로 전환하며 필요한 패키지와 의존성을 점검했습니다. 이후 저장소의 다른 경로에 이미 양자화된 데이터와 구현 파일이 있다는 사실을 확인해 중복 작업을 중단하고 기존 파일을 활용했습니다.

OpenROAD 역시 Ubuntu VM에서 실행했습니다. OpenROAD 저장소를 fork한 뒤 CNN RTL 저장소를 하위 저장소로 연결했으며, 실행 과정에서 필요한 추가 의존 저장소도 각각 fork해 프로젝트 구조에 포함했습니다. 이를 통해 여러 저장소와 하위 모듈로 구성된 합성 환경을 직접 구축했습니다.

초기 실행에서는 설계를 배치할 영역이나 자원이 부족하다는 취지의 오류가 발생했습니다. 실행 로그를 확인하며 Core Utilization, Placement Density 등 배치 관련 설정을 하나씩 변경했습니다. 한 번의 실행에 오랜 시간이 필요했기 때문에 실패 단계와 변경한 조건을 기록하며 다음 시도의 설정을 결정했고, 여러 차례 조정한 끝에 합성 단계를 통과해 결과 Verilog Netlist를 확보했습니다.

이후 생성된 Netlist에 테스트벤치를 적용해 기존 RTL과 동일하게 동작하는지 확인했지만, 시뮬레이션 결과가 정상적으로 나오지 않았습니다. 합성 결과와 검증 환경을 추가로 분석해야 했으나, 환경 구축과 장시간의 OpenROAD 실행에 프로젝트 기간 대부분을 사용해 원인을 해결하지는 못했습니다. 다만 익숙하지 않은 도구를 사용하기 위해 실행 환경과 저장소 의존성을 직접 구성하고, 로그를 바탕으로 설정을 반복 조정하며 합성 결과와 후속 검증 단계까지 도달했습니다.

두 과제에서 모든 문제를 완전히 해결하지는 못했지만, 신호와 시뮬레이션 결과, 실행 로그를 근거로 이상이 발생한 구간을 단계적으로 좁혔습니다. 이를 통해 복잡한 시스템에서는 추측보다 재현 가능한 결과를 기준으로 원인을 하나씩 배제하는 검증 과정이 중요하다는 점을 배웠습니다. Product Engineering 직무에서도 테스트 결과와 제품 데이터를 근거로 이상 원인을 좁히고, 신뢰할 수 있는 개선 방향을 찾겠습니다.

## 1. 지원하신 직무 분야의 전문성을 키우기 위해 꾸준히 노력한 경험에 대해 서술해주세요. (600자)

디지털 시스템을 신호 단위로 이해하고 검증하는 역량을 꾸준히 키웠습니다. 2학년 때 컴퓨터구조를 처음 배웠지만 이론만으로는 데이터 경로와 제어 흐름을 충분히 이해하기 어려웠습니다. 이를 보완하고자 4학년 1학기에 논리회로설계와 마이크로프로세서를 함께 수강했습니다. 논리회로설계에서는 HDL과 Verilog를 익히고, 과목의 개인 과제로 Logisim 기반 단일 사이클 CPU를 Verilog로 구현했습니다. 직접 회로를 모듈로 나누고 연결하면서 이전에는 추상적으로 느껴졌던 프로세서의 데이터 흐름과 제어 구조를 구체적으로 이해할 수 있었습니다.

과제 검증을 위해 테스트벤치와 TCL 스크립트를 작성하고, 동일한 입력에서 Logisim을 한 tick씩 실행하며 ModelSim 파형과 비교했습니다. 최초 불일치 지점부터 신호를 역추적해 ALU 입력 순서, ADDI·ANDI 제어식, CP0 연결 오류를 수정했습니다. EPC 문제는 완전히 해결하지 못했지만 래치 동작과 신호 변화 시점으로 범위를 좁혔습니다. 이러한 구현 경험을 바탕으로 마이크로프로세서 과목의 ARM 명령어와 프로세서 구조도 더 구체적으로 이해했고, 두 과목 모두 A를 받았습니다.

## 2. 팀워크를 발휘해 사람들을 연결하고 공동 목표 달성에 기여한 경험에 대해 서술해주세요. (600자)

종합설계프로젝트 과목의 LG 산학연계 프로젝트에서 Raspberry Pi에 webOS OSE를 올리고 AWS로 외부 웹앱과 연동한 스마트 화분을 개발했습니다. 기능이 많아 팀원들은 강점에 따라 React UI, AWS, JsService, Arduino 제어를 나눠 맡았습니다. 저는 고등학생 때부터 Arduino와 Raspberry Pi를 다뤄온 경험을 살려 센서 측정, 네오픽셀 조명, 워터펌프 제어를 구현했습니다.

통합 단계에서는 JsService가 보낼 제어 명령, Arduino의 실행 결과, 센서 반환값을 표로 정리해 담당자들과 공통 명세를 확정했습니다. 이어 팀원이 만든 UI 틀에 제가 정리한 값을 불러와 표시하는 코드를 적용했습니다. 값이 어긋나면 Arduino 출력, JsService 전달값, 화면 표시값을 각 담당 팀원과 순서대로 대조했습니다.

그 결과 센서 확인과 급수, 조명 제어를 OSE 앱과 외부 웹앱에서 사용할 수 있도록 연결했습니다. 이후 프로젝트를 발전시켜 임베디드 소프트웨어 경진대회에 출품했고 webOS 부문 입선을 달성했습니다. 각자의 강점을 살린 역할 분담과 결과물이 만나는 기준을 함께 맞추는 것이 팀워크의 핵심임을 배웠습니다.

## 3. 도전적인 목표를 세우고 성취하기 위해 끈질기게 노력한 경험에 대해 서술해 주세요. (600자)

시각장애인이 사용할 수 있는 코딩 교육 앱을 출시하겠다는 목표로 허밍블럭스 개발을 시작했습니다. 당시 Android와 AI 연동 경험이 거의 없었지만, 아이디어 시연에 그치지 않고 Google Play 출시까지 완성하겠다고 정했습니다.

개발 과정에서는 같은 블록이 중복 인식되고 실행 순서가 뒤섞이는 문제가 반복됐습니다. 저는 오류가 난 사진과 결과를 유형별로 모아 원인을 비교하고, 촬영, 객체 인식, 후처리, 음악 실행 단계로 나눠 하나씩 수정했습니다. NMS로 중복 결과를 제거하고 위치값을 기준으로 실행 순서를 다시 정렬했으며, 수정할 때마다 여러 기기에서 같은 사진을 반복 테스트했습니다.

추론 지연을 줄이기 위해 TensorFlow Lite도 적용했습니다. 처리 시간은 9.1초에서 5.4초로 줄었지만 정확도가 90%에서 57%로 떨어졌습니다. 개선 시도가 원하는 결과로 이어지지 않았지만, 서비스에는 정확도가 더 중요하다고 판단해 Chaquopy 방식으로 돌아가 검증을 이어갔습니다. 약 1년간 시행착오를 반복한 끝에 앱 출시와 판매를 이뤘고, 창업경진대회 대상도 받았습니다. 문제를 한 번에 해결하려 하기보다 기록하고 비교하며 끝까지 완성하는 끈기를 배웠습니다.

## 4. 지원자님은 어떤 사람인가요? 지원자님을 가장 잘 나타낼 수 있는 해시태그(#)를 포함하여 자유롭게 표현해주세요. (선택, 600자)

#원인을파고드는사람

문제가 생기면 보이는 결과만 고치지 않고 값이 처음 어긋난 지점부터 확인합니다. Verilog 단일 사이클 CPU를 구현할 때 예외 처리 뒤 복귀 주소가 달라지는 문제가 있었습니다. PC와 예외 신호, EPC 값을 클럭별로 비교해 저장 시점의 오류를 찾았고, 수정 후에는 전체 명령어와 RTL, Netlist 결과를 다시 점검했습니다. 원인을 파고든다는 것은 오래 붙잡는 일이 아니라, 근거를 바탕으로 범위를 좁혀 결과를 책임지는 태도라고 생각합니다.

#빈틈을먼저채우는사람

허밍블럭스 개발 중 디자이너의 이미지 리소스 전달이 늦어지며 화면 구현 일정이 멈출 상황이 있었습니다. 기다리기보다 필요한 화면과 규격을 먼저 확인한 뒤 Lottie 파일을 GIF로 변환하고, 프레임을 분리해 필요한 장면을 PNG로 추출했습니다. 앱 화면에 맞도록 크기와 위치를 조정하고, 시각적 구분이 필요한 이미지는 밝기를 보정해 임시 리소스로 적용했습니다. 이후 디자이너와 결과를 공유해 의도와 다른 부분을 수정하고 최종 리소스로 교체할 수 있도록 정리했습니다. 맡은 역할만 지키기보다 팀의 진행을 막는 빈틈을 먼저 찾아 채우며 공동의 결과를 완성하겠습니다.
