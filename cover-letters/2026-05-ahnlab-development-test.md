## 1. 본인이 지원하는 직무에 관심을 갖게 된 계기와 이 직무를 수행하기 위해 어떤 노력을 했는지 작성해 주세요. (700자)

기능을 한 번 구현하고 끝내기보다, 실제 사용 흐름에서 의도한 결과가 나올 때까지 반복해서 확인하고 고쳐가는 과정에 흥미를 느껴 개발 및 테스트 직무에 관심을 갖게 되었습니다. 특히 사용자가 결과를 눈으로 확인하기 어려운 상황이라면, 기능이 정확하게 이어지는지 세심하게 검증해야 한다고 생각했습니다.

이런 관점으로 접근했던 경험이 허밍블럭스였습니다. 허밍블럭스는 화면 중심의 코딩 교육에서 결과 확인이 어려운 시각장애 학습자를 위해, 실물 블록을 촬영하면 이를 인식해 음악으로 실행하는 앱입니다. 앱을 만들며 촬영, 블록 인식, 음악 실행으로 이어지는 흐름을 구현했습니다. 하지만 테스트 과정에서 음악이 의도한 대로 나오지 않는 문제가 있었습니다. 여러 번 실행 결과를 확인하며 일부 블록이 다른 블록과 연결된 것으로 처리되지 않는 원인을 찾았고, 인식 결과를 음악 실행에 맞게 처리하는 후처리 알고리즘을 수정했습니다. 이후 다양한 블록 조합으로 반복 테스트하며 원하는 흐름대로 작동하는지 확인했습니다.

이 경험을 통해 개발과 테스트는 따로 떨어진 일이 아니라, 사용자가 믿고 사용할 수 있는 기능을 완성하기 위한 하나의 과정이라고 배웠습니다. 안랩의 보안 제품은 확인하기 어려운 보안위협으로부터 시스템을 보호하므로 신뢰성이 매우 중요하다고 생각합니다. 원하는 기준에 도달할 때까지 반복 확인하는 태도로 정확하고 안정적인 제품 개발에 기여하겠습니다.

## 2. 그 밖에 본인에 대해 어필하고 싶은 부분을 자유롭게 작성해 주세요. (700자)

기능이 겉으로 동작하는 것을 확인하는 데서 멈추지 않고, 그 아래에서 어떤 구조로 결과가 만들어지는지 직접 확인해야 만족하는 성향이 있습니다. 이 성향은 Verilog CPU 프로젝트에서 잘 드러났습니다. 해당 프로젝트는 Logisim으로 구현된 single cycle CPU를 참고해 Verilog로 다시 구현하고, 같은 명령어를 실행했을 때 동일한 결과가 나오는지 확인하는 과제였습니다.

모듈별로 기능을 구현한 뒤 전체 CPU로 연결했지만, 일부 명령어에서 예상과 다른 결과가 나왔습니다. 이때 출력값만 맞추려 하지 않고 명령어가 fetch, decode, execute 단계를 거치며 어떤 신호로 전달되는지 확인했습니다. 하위 모듈의 입력과 출력, 제어 신호의 연결을 따라간 결과 ALU 입력 순서가 잘못 연결된 문제와 CP0 예외 처리에서 EPC 정의가 맞지 않는 문제를 찾을 수 있었습니다. 이를 수정하며 정확한 구현은 겉으로 보이는 동작뿐 아니라 시스템 내부 구조를 이해할 때 가능하다는 점을 배웠습니다.

이후에도 낯선 기술을 다룰 때 전체 흐름을 나누고, 각 단계가 어떤 역할을 하는지 확인하려고 했습니다. 안랩의 보안 제품도 운영체제, 파일, 네트워크 등 낮은 수준의 동작과 맞물려 사용자의 시스템을 보호한다고 생각합니다. 보이는 결과에 만족하지 않고 내부 원리를 확인하는 태도로 제품의 안정성과 신뢰성을 높이는 개발자가 되겠습니다.
