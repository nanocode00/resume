# 커밋 기반 경험 복원 가이드

이 문서는 프로젝트 경험을 커밋 단위로 다시 확인하면서 `상황 → 문제 → 판단 → 조치 → 결과`를 복원하는 작업 절차를 정리합니다.

`resume-experience-writing.md`가 이력서와 경험기술서의 작성 원칙을 다룬다면, 이 문서는 **기존 프로젝트 기록을 어떻게 조사하고 사실관계를 복원할지**에 집중합니다.

## 1. 한 번에 너무 넓게 보지 않습니다

프로젝트 전체를 한 번에 정리하지 않습니다.

권장 범위:

- 커밋 3~5개
- 또는 하나의 기능 흐름
- 또는 하나의 문제 해결 에피소드

예:

- MIPS CPU: `Opcode Decoder → ALU → Register File`
- 다음 작업: `SingleCycleCPU → CP0/Syscall → cleanup`
- webOS Smart Planter: Arduino/I2C firmware → webOS HW integration
- HummingBlocks: TFLite 전환 실험만 별도 조사

커밋이 많거나 운영 기간이 긴 프로젝트는 여러 묶음으로 나눕니다.

## 2. 커밋에서 바로 경험 문장을 만들지 않습니다

기본 흐름은 다음과 같습니다.

`commit → 사실 복원 → 기억/자료 확인 → 경험 문장`

코드 diff는 주로 **조치**를 잘 보여주지만, **상황·문제·판단**은 diff만으로 단정하기 어렵습니다.

따라서 기술 변경을 보고 원인을 추측해서 바로 이력서 문장으로 만들지 않습니다.

## 3. 한 묶음마다 먼저 확인할 것

각 커밋 묶음에서 다음을 조사합니다.

1. author와 날짜
2. branch와 앞뒤 commit
3. 실제 diff
4. 변경된 파일과 모듈
5. README, worklog, issue, PR, test log
6. 당시 발표자료, 보고서, Drive 자료
7. 이전 대화 기록이나 본인 기억
8. 이후 commit에서 해당 변경이 유지됐는지 또는 되돌아갔는지

commit message는 탐색용으로만 사용하고, 기술적 결론은 가능한 한 diff와 후속 결과로 확인합니다.

## 4. 각 커밋을 5단계로 임시 복원합니다

### 상황

당시 어떤 기능이나 단계의 개발을 진행하고 있었는지 정리합니다.

확인 예:

- 처음 구현하는 단계인지
- 기존 구현을 교체하는 실험인지
- 통합 직전인지
- bug fix인지
- 실제 사용 이후 유지보수인지

### 문제

왜 이 변경이 필요했는지 찾습니다.

근거 우선순위:

1. 당시 문서/issue/worklog에 직접 적힌 문제
2. test/log에서 관찰되는 문제
3. 앞뒤 diff에서 명확히 드러나는 문제
4. 본인의 기억
5. 코드 구조를 바탕으로 한 추정

4~5번 수준이면 확정 표현을 쓰지 않습니다.

### 판단

여러 방법 중 왜 해당 방법을 선택했는지 찾습니다.

예:

- 정확도보다 latency가 중요한가
- latency보다 정확도가 중요한가
- 기존 구조를 수정할지 새 branch에서 실험할지
- 큰 모델 대신 작은 모델을 선택한 이유
- LLM 대신 deterministic logic을 둔 이유
- 최종 output보다 intermediate result를 비교한 이유

판단 근거가 문서에 없으면 `기억 확인 필요`로 둡니다.

### 조치

실제 코드 변경을 가능한 한 구체적으로 적습니다.

좋은 형태:

- `weight.detach()`를 `weight().int_repr()`로 변경
- `reg + always` parameter unpacking을 `wire + generate + assign`으로 변경
- Chaquopy/Python inference를 TFLite/Java로 이식
- NLU를 별도 venv와 HTTP sidecar로 분리

`리팩터링했다`, `최적화했다`처럼 diff를 설명하지 못하는 추상 표현은 피합니다.

### 결과

이후 commit, test, benchmark, 발표자료에서 실제 결과를 확인합니다.

가능하면 다음을 적습니다.

- 성공 여부
- 수치 변화
- 최종 채택 여부
- 이후에도 유지됐는지
- 되돌렸다면 왜 되돌렸는지
- 실패했다면 어디까지 성공했는지

결과가 없으면 `결과 미확인`으로 남기고 억지로 결론을 만들지 않습니다.

## 5. 불확실한 내용은 본인 기억으로 보완합니다

조사 후에도 남는 질문만 본인에게 확인합니다.

좋은 질문:

- 이 변경은 성능 문제 때문이었는지, 기능 bug 때문이었는지
- 두 방식 중 한쪽을 버린 결정적 이유가 무엇이었는지
- 당시 benchmark를 어떤 환경에서 측정했는지
- 팀원이 만든 코드와 본인이 직접 수정한 범위가 어디까지인지

좋지 않은 방식:

- 프로젝트 전체를 다시 설명해 달라고 요청
- 이미 Git에서 확인 가능한 내용을 다시 질문
- 답을 유도하는 식으로 기억을 맞추려 하기

먼저 source로 범위를 최대한 좁힌 뒤 기억을 보완 자료로 사용합니다.

## 6. 사실 확정 수준을 구분합니다

각 정보는 내부적으로 다음처럼 구분합니다.

### A. 직접 확인

- Git diff
- test/log
- 최종 코드
- 발표자료/보고서 원본

### B. 기록으로 확인

- 당시 또는 이후 작성한 경험기술서
- worklog
- 본인 대화 기록

### C. 본인 기억으로 확인

- 당시 의사결정 이유
- 문서에 남지 않은 팀 상황

### D. 추정

- 코드 구조만 보고 유추한 이유

이력서에는 A/B를 우선 사용하고, C는 다른 자료와 모순되지 않을 때 사용합니다. D는 경험 문장으로 확정하지 않습니다.

## 7. 한 묶음을 끝내는 기준

다음이 확인되면 해당 커밋 묶음을 닫습니다.

- 상황이 무엇이었는지 설명 가능
- 실제 문제가 무엇인지 설명 가능
- 선택 기준 또는 판단 이유가 확인됨
- 어떤 코드/구조를 바꿨는지 diff로 설명 가능
- 결과 또는 실패 지점이 확인됨
- 개인 기여와 팀 기여가 구분됨

하나라도 중요한 부분이 비어 있으면 `추가 확인 필요`로 남기고 다음 묶음과 섞지 않습니다.

## 8. 문서 반영 순서

조사가 끝나면 다음 순서로 반영합니다.

1. `experiences/*.md`에 상세 근거와 5단계 흐름 기록
2. 중복되는 여러 commit은 하나의 의미 있는 문제 해결 episode로 묶음
3. source provenance와 주의할 표현을 함께 기록
4. `resume.md`에는 가장 강한 판단과 결과만 압축
5. 자기소개서에서는 지원 문항에 필요한 episode만 선택

모든 commit을 이력서에 나열하지 않습니다.

## 9. 프로젝트별 권장 조사 순서

작은 프로젝트부터 방법을 검증합니다.

1. **MIPS SingleCycleCPU**
   - 직접 commit 수가 적고 보고서/ModelSim 자료가 있어 첫 forensic 작업에 적합
2. **webOS Smart Planter**
   - firmware → I2C → webOS integration 흐름이 비교적 명확
3. **CNN Accelerator**
   - Python/RTL/OpenROAD 세 저장소와 submodule 관계가 있어 기능 흐름별 분할 필요
4. **HummingBlocks**
   - 개발 기간이 길고 commit 수가 많으므로 TFLite, 음악 재생, migration, 접근성 등으로 여러 번 분할
5. **Mallo**
   - PR/worklog/대화 기록이 많아 모델, UI, runtime, deployment 단위로 나눠 추가 조사 가능

실제 우선순위는 새 자료가 발견되거나 지원 직무에 따라 바꿀 수 있습니다.

## 11. 대규모·장기 프로젝트는 먼저 개발작업 원장을 만듭니다

HummingBlocks처럼 여러 해 동안 개발했고 branch와 commit이 많은 프로젝트는 곧바로 경험기술서를 쓰지 않습니다.

먼저 **개발작업 원장**을 만듭니다.

권장 단위:

- 개인 작업: `PROJECT-01`, `PROJECT-02`처럼 연속 ID
- 팀 선행 작업: `PRE-*`
- 다른 팀원 구현: `TEAM-*`
- 포트폴리오용 상위 묶음: `GROUP-*`

각 개인 작업에는 최소한 다음을 기록합니다.

| 항목 | 내용 |
|---|---|
| ID | 추적 가능한 고유 작업 번호 |
| 시기 | 정확한 날짜 또는 대략적인 기간 |
| 작업 | 실제 해결한 문제 단위의 제목 |
| 대표 근거 | commit SHA, 파일, 문서 |
| 소유권 | 직접 구현 / 팀 구현 / 공동 기획 / 실험 |
| 우선순위 | 포트폴리오 상세화 가치 |

중요한 점은 **commit 수와 개발작업 수를 동일하게 보지 않는 것**입니다.

하나의 기능이 여러 bugfix·UI polish·revert·재적용 commit으로 이어질 수 있고, 반대로 하나의 큰 commit 안에 여러 독립 기능이 섞일 수도 있습니다.

따라서 ID는 commit이 아니라 **문제 해결 단위**에 붙입니다.

## 12. 전체 commit graph로 누락을 역검증합니다

작업 목록이 어느 정도 만들어졌다고 끝내지 않습니다.

장기 프로젝트에서는 마지막에 다음 검증을 반드시 합니다.

1. 모든 branch를 열거합니다.
2. branch 간 중복 SHA를 제거해 unique commit 집합을 만듭니다.
3. 본인 author의 non-merge commit을 분리합니다.
4. 이미 작업 원장에 대표 SHA로 등장하는 commit을 제외합니다.
5. 남은 **미매핑 commit을 전부 역검토**합니다.
6. 새 독립 작업인지, 기존 작업의 후속 수정인지 분류합니다.

미매핑 commit은 다음 중 하나로 흡수될 수 있습니다.

- 기존 기능의 bugfix
- asset 교체
- UI polish
- release maintenance
- revert / 재적용
- 다른 branch에서 같은 작업을 진행한 병렬 SHA
- 테스트용 PoC
- 실제로 빠져 있던 독립 개발작업

이 절차의 목적은 모든 commit을 이력서에 넣는 것이 아니라 **중요한 개인 작업이 빠지지 않았음을 확인하는 것**입니다.

`commit message가 새로워 보인다 → 새 경험`으로 바로 판단하지 않습니다.

## 13. 역할 소유권을 기능별로 분리합니다

팀 프로젝트에서는 최종 코드에 본인 commit이 많다는 이유만으로 전체 기능을 개인 구현으로 쓰지 않습니다.

다음 범위를 구분합니다.

- **문제·규칙 설계:** 누가 요구사항이나 규칙을 정의했는가
- **최초 구현:** 최초 동작 코드를 누가 만들었는가
- **제품 통합:** prototype을 실제 제품 흐름에 누가 연결했는가
- **리팩터링·안정화:** 오류 계약, 상태 관리, 예외 처리를 누가 보강했는가
- **자산 제작:** 디자인·음원·모델 등의 원본을 누가 만들었는가
- **후속 운영:** migration, release, compatibility를 누가 담당했는가

예를 들어 다음은 서로 다른 기여입니다.

- 팀원이 Python prototype을 최초 구현
- 본인이 그 결과를 Android에서 호출하도록 통합
- 팀 회의에서는 본인이 블록 규칙 설계 의견을 주도
- 디자이너가 Figma를 만들고 본인이 ConstraintLayout으로 구현
- 팀원이 CameraX prototype을 만들고 본인이 저장·상태·오류 흐름을 제품화

이 경우 `전체 기능을 구현했다`보다 각 단계의 실제 책임을 분리해 쓰는 것이 더 정확하고, 면접에서도 설명하기 쉽습니다.

## 14. 세부 티켓을 그대로 포트폴리오로 쓰지 않습니다

작업 원장은 **근거 레이어**입니다.

조사가 끝나면 비슷한 문제를 해결한 티켓들을 상위 작업군으로 다시 묶습니다.

좋은 통합 기준:

- 같은 문제를 여러 차례 개선한 작업
- 동일한 상태나 데이터 모델을 공유하는 기능
- 하나의 사용자 흐름을 완성하는 기능
- 실험 → 측정 → 채택/rollback으로 이어지는 작업

예:

`초기 MediaPlayer 실험 → pause/resume → scheduler 재설계 → BPM → countdown`

이들을 commit별 5개 경험으로 쓰는 대신 **실시간 재생 엔진의 진화**라는 하나의 이야기로 묶을 수 있습니다.

반대로 해결하려는 문제가 완전히 다르면 억지로 합치지 않습니다.

예:

- 반응형 UI
- TFLite inference 실험
- 데이터 migration

은 같은 Android 앱 작업이어도 별도 문제입니다.

## 15. Canonical 프로젝트 문서를 먼저 만듭니다

작업 원장 검증이 끝난 뒤에는 하나의 **사실 기준 원본 문서(canonical document)**를 만듭니다.

이 문서의 목적은 채용 담당자에게 바로 보여주는 것이 아니라, 이후 모든 이력서·포트폴리오 문구가 여기서 파생되도록 만드는 것입니다.

권장 구조:

1. 프로젝트 개요
2. 역할과 기여 경계
3. 전체 기술 흐름 / architecture
4. 통합된 개발 경험
5. 시간순 요약
6. 검증 가능한 결과와 수치
7. 표현 시 주의할 주장
8. 세부 작업 ID 인덱스
9. 근거 문서·저장소

세부 티켓을 본문에 전부 펼치지 않습니다.

본문에서는 기술적 진화를 읽을 수 있게 묶고, 맨 아래 ID 인덱스로 다시 세부 근거까지 추적할 수 있게 합니다.

이렇게 하면 다음 두 요구를 동시에 만족합니다.

- 사람은 프로젝트 전체 맥락을 쉽게 읽을 수 있음
- 나중에 문장 하나의 근거를 commit까지 다시 추적할 수 있음

## 16. 포트폴리오는 문제 해결의 깊이로 4~6개만 선별합니다

canonical 문서가 완성된 뒤에야 포트폴리오 경험을 고릅니다.

선별 기준:

1. **문제의 깊이** — 단순 기능 추가보다 원인과 제약이 분명한가
2. **판단** — 여러 방법 중 무엇을 왜 선택했는가
3. **구현 난이도** — 상태·동시성·성능·호환성 등 기술적 깊이가 있는가
4. **제품 연결성** — 실제 사용자 흐름이나 출시 제품으로 이어졌는가
5. **검증 가능성** — 코드·로그·수치·rollback이 근거로 남아 있는가

대표 경험은 다음 형식으로 압축합니다.

`문제 → 판단 → 구현 → 결과`

모든 좋은 작업을 대표 사례로 올릴 필요는 없습니다.

예를 들어 반응형 UI나 asset packaging처럼 의미 있는 작업도 더 강한 제품화 경험을 보강하는 **서브 사례**로 배치할 수 있습니다.

## 17. 실패·미채택·rollback도 독립적인 경험 자산입니다

새 구현이 최종 제품에 들어가지 않았다고 삭제하지 않습니다.

다음 흐름이 확인된다면 오히려 좋은 경험입니다.

`가설 → 별도 구현 → 비교 → 문제 확인 → 미채택/rollback`

특히 다음을 설명할 수 있어야 합니다.

- 왜 실험했는가
- 기존 방식과 무엇이 달랐는가
- 어떤 지표로 비교했는가
- 무엇이 개선됐는가
- 무엇이 악화됐는가
- 왜 최종적으로 채택하지 않았는가

`새 기술을 적용했다`보다 **제품 기준에 맞지 않아 되돌린 판단**이 더 좋은 설명이 될 수 있습니다.

## 18. 정량 수치는 측정 조건까지 하나의 사실로 봅니다

숫자가 기록돼 있다고 바로 성과 수치로 쓰지 않습니다.

확인해야 할 것:

- 장비
- sample 수
- 반복 횟수
- 데이터셋
- baseline
- 집계 방식
- 측정 시점
- 원본 log/table 존재 여부

예를 들어 `9.1s → 5.4s`가 남아 있어도 여러 기기에서 각각 1회 측정한 값이라면 `평균 benchmark`라고 표현하지 않습니다.

정확도 수치가 남아 있지만 데이터셋·샘플 수가 확인되지 않는다면:

- canonical 문서에는 `당시 기록값`으로 보존
- 포트폴리오에서는 조건을 명시하거나 정량 수치 자체를 제외
- 이력서에서는 의사결정만 남기는 것도 가능

즉 **숫자와 그 숫자가 의미하는 범위를 함께 검증**합니다.

## 19. 작업 종료 기준

대규모 프로젝트 정리는 다음 상태가 되면 종료할 수 있습니다.

- [ ] 전체 branch/commit graph를 확인했다.
- [ ] 개인 작업이 문제 단위 ID로 정리됐다.
- [ ] 미매핑 개인 commit을 역검토했다.
- [ ] 팀 선행 구현과 개인 구현 범위가 분리됐다.
- [ ] 같은 문제의 여러 commit을 상위 작업군으로 통합했다.
- [ ] canonical 프로젝트 문서가 작성됐다.
- [ ] 검증되지 않은 수치와 추정이 표시됐다.
- [ ] 포트폴리오 대표 경험 4~6개를 선별했다.
- [ ] resume에는 대표 판단과 결과만 압축했다.
- [ ] 최종 변경을 PR로 검토한 뒤 main에 반영했다.

이 단계가 끝난 뒤에는 세부 조사 문서를 지우지 않습니다. 미래의 지원서, 면접 준비, 포트폴리오 수정에서 다시 근거로 사용할 수 있기 때문입니다.

## 20. 가장 중요한 원칙

- **commit 수 ≠ 개발작업 수**입니다.
- 코드에서 확인되지 않는 의도를 임의로 만들지 않습니다.
- 기억을 무시하지 않지만, 기억만으로 기술적 사실을 확정하지 않습니다.
- 최초 구현자와 제품화·통합 담당자를 구분합니다.
- 팀 기획, 외부 asset, 개인 구현의 경계를 유지합니다.
- 성공한 변경만 찾지 않고 되돌린 실험과 실패도 조사합니다.
- 수치는 값뿐 아니라 측정 조건까지 검증합니다.
- 미매핑 commit을 마지막에 역검토해 누락을 확인합니다.
- 모든 세부 작업을 포트폴리오에 올리지 않습니다.
- canonical 문서를 먼저 만들고 이력서·포트폴리오는 그 문서에서 파생합니다.
- 결과가 없는 경험은 결과를 만들어내지 않습니다.
- 최종 목적은 커밋 목록을 만드는 것이 아니라 **어떤 상황에서 어떤 문제를 발견하고, 어떤 기준으로 판단해 무엇을 바꿨으며, 결과가 어떻게 됐는지 근거와 함께 설명할 수 있게 만드는 것**입니다.
