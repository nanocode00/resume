# 자기소개서 작성 가이드

이 문서는 실제 지원서를 작성할 때 반복해서 적용할 개인 작성 규칙과 작업 순서를 정리합니다.

## 1. 분량 규칙

- 글자 수 제한은 **공백 포함 한글 기준으로 정확히 계산**합니다.
- 1,000자 제한이라면 가능한 한 **980~1,000자** 범위까지 채웁니다.
- 바이트 제한이면 한글 2바이트, ASCII 1바이트 기준으로 계산하고 최대치에서 지나치게 짧지 않게 작성합니다.
- 한 문단으로 길게 쓰지 않고 내용의 전환점마다 문단을 나눕니다.

## 2. 문체 규칙

- 문장 첫 단어로 `저는`을 사용하지 않습니다.
- 본문에서도 `저는`은 가능한 한 줄입니다.
- 너무 어렵거나 과장된 단어를 피합니다.
- `단순히`라는 표현을 사용하지 않습니다.
- 같은 키워드를 과하게 반복하지 않습니다.
- `이러한 생각은 ~를 통해 더욱 분명해졌습니다`와 같은 상투적인 연결 문장을 쓰지 않습니다.
- 여러 항목을 나열할 때 가운데점 `·`을 사용하지 않습니다. 쉼표나 문장 구조로 자연스럽게 풀어 씁니다.

## 3. 경험 사용 규칙

자소서에서 경험 이름만 언급하지 않습니다. 해당 경험을 처음 보는 사람도 이해할 수 있도록 최소한 다음 내용을 포함합니다.

- 어떤 프로젝트 또는 상황이었는지
- 본인이 맡은 역할이 무엇이었는지
- 어떤 문제나 목표가 있었는지
- 어떤 판단과 행동을 했는지
- 결과가 어떻게 달라졌는지

경험의 세부 사실은 `../experiences/`의 원본 파일을 우선 참고합니다.

## 4. 경험 서술의 기본 원칙

앞으로 이력서, 경험기술서, 자기소개서의 기술 경험은 가능한 한 **상황 → 문제 → 판단 → 조치 → 결과** 순서로 정리합니다.

### 상황

프로젝트 이름이나 기술 이름부터 나열하지 않고, 처음 읽는 사람도 이해할 수 있도록 무엇을 만들었고 어떤 환경이었는지 짧게 설명합니다.

반드시 구분할 것:

- 팀 규모
- 프로젝트 기간
- 본인 역할
- 기존 코드 또는 공개 baseline을 사용한 경우 그 범위
- 회사 또는 팀 전체 성과와 개인 기여

### 문제

`성능이 좋지 않았다`, `오류가 있었다`처럼 추상적으로 쓰지 않습니다. 가능하면 실제 관찰값과 조건을 함께 적습니다.

예:

- Galaxy S9+에서 평균 추론 시간이 9.1초
- ModelSim 1,000-image RTL simulation에서 96% accuracy
- gate-level simulation에서 정상 waveform 확보 실패
- 두 Python runtime의 `transformers` 요구 버전 충돌

문제가 여러 개라면 하나의 문장에 모두 섞지 않고 **사용성, 정확도, latency, dependency, 합성, timing 등 문제 종류를 분리**합니다.

### 판단

무엇을 했는지보다 **왜 그 방법을 선택했는지**를 반드시 남깁니다.

좋은 판단 문장에는 비교 대상과 기준이 있습니다.

- 속도보다 정확도가 제품에서 더 중요한가
- 큰 모델보다 interactive latency가 더 중요한가
- LLM이 상태를 직접 바꾸는 것보다 deterministic logic으로 분리하는 것이 안전한가
- 최종 output만 보는 것보다 intermediate layer/MAC을 비교하는 것이 원인 추적에 유리한가

`최신 기술이라 선택했다`, `성능이 좋아 보여 사용했다`처럼 기준이 없는 표현은 피합니다.

### 조치

기술 스택을 나열하는 대신 **실제 변경한 코드나 구조**를 적습니다.

예:

- Chaquopy/Python inference를 TFLite + Java로 이식
- confidence filtering, NMS, 위치 기반 후처리까지 Java로 이동
- quantized Tensor를 `int_repr()` 기반 HW reference로 변환
- `reg + always` parameter unpacking을 `generate + assign`으로 변경
- LLM과 Cart state를 분리하고 deterministic Order Engine 구현
- dependency가 충돌하는 모델을 별도 venv와 resident sidecar로 분리

가능하면 실제 커밋을 확인해 조치를 복원합니다. 기억만으로 기술적인 원인을 확정하지 않습니다.

### 결과

결과는 가능하면 **숫자, 비교 전후, 성공 여부**로 끝냅니다.

좋은 결과:

- 9.1s → 5.4s, 약 40.7% 단축
- 정확도 90% → 57%, -33%p
- MeloTTS 204ms vs Qwen3-TTS 6.91~28.20s
- MNIST 1,000장 RTL accuracy 96%
- final STA slack -2040.66, VIOLATED

성공하지 못한 결과도 숨기지 않습니다. `정상 waveform 미확보`, `timing closure 실패`, `수수료 반영 후 전략 붕괴`처럼 **검증한 한계와 실패 지점**이 명확하면 좋은 경험으로 사용할 수 있습니다.

## 5. 수치와 근거 사용 원칙

### 수치는 맥락과 함께 씁니다

숫자만 적지 않고 다음 조건을 가능한 한 함께 남깁니다.

- 측정 장비 또는 환경
- 데이터 수 또는 평가 sample 수
- baseline
- 비교 대상
- 단위
- 측정 조건이 다른 결과인지 여부

예를 들어 `96% accuracy`보다 `ModelSim에서 MNIST 1,000장 기준 RTL accuracy 96%`가 더 정확합니다.

### 비교 실험은 반드시 최종 선택까지 연결합니다

여러 모델이나 구현을 비교했다면 다음 네 가지를 남깁니다.

1. 어떤 후보를 비교했는가
2. 어떤 지표를 사용했는가
3. 결과가 어떻게 달랐는가
4. 그래서 무엇을 선택했고 왜 선택했는가

`모델 A와 B를 비교했다`에서 끝내지 않습니다.

### 수치가 의사결정으로 이어져야 합니다

숫자를 많이 넣기 위한 숫자는 쓰지 않습니다.

예:

- TFLite가 빨라졌지만 정확도가 33%p 하락해 제품에는 미채택
- MeloTTS fine-tuning 후 latency가 2.8% 늘었지만 interactive latency를 유지해 tone adaptation을 선택
- 분류 정확도가 나와도 거래 수수료 적용 후 손실이면 실사용 전략으로 부적합

### 원본 근거가 유실된 수치는 상태를 표시합니다

당시 실제 측정한 값이어도 원본 Excel, log, report를 찾지 못하면 이를 숨기지 않습니다.

구분 예시:

- `Git log로 직접 확인`
- `최종 발표자료로 확인`
- `당시 측정 후 이후 경험기술서에 기록한 값`
- `회사/제품의 후속 누적 실적`
- `원본 benchmark sheet 추가 확인 필요`

원본이 없는 수치를 새로 계산한 값처럼 표현하지 않습니다.

## 6. 기여 범위와 성과 귀속 원칙

팀 또는 제품의 성과를 개인 성과처럼 쓰지 않습니다.

반드시 구분합니다.

- 내가 직접 작성하거나 수정한 코드
- 팀원이 주도하고 내가 통합 또는 추가 검증한 영역
- 기존 공개 baseline
- 회사/제품 전체 성과
- 프로젝트 종료 이후 누적된 후속 성과

예:

- `누적 키트 판매 1,830개`가 이후 회사 사업계획서의 제품 누적 실적이면 `내가 1,830개를 판매했다`고 쓰지 않습니다.
- STT Lead가 따로 있다면 `STT 전체 학습 파이프라인 담당`이 아니라 `후반 candidate sweep과 production 선정에 직접 참여`라고 씁니다.
- 공개 CNN RTL을 baseline으로 사용했다면 `CNN Accelerator 전체 RTL을 처음부터 설계`했다고 쓰지 않습니다.

성과가 강해 보이는 것보다 **검증 가능한 기여 범위를 정확히 쓰는 것**을 우선합니다.

## 7. 커밋 기반 경험 복원 원칙

기술 경험을 다시 정리할 때 README만 보지 않고 가능한 한 세부 commit을 확인합니다.

확인 순서:

1. 프로젝트 시작 시점의 baseline과 기존 구조 확인
2. 본인 author commit 분리
3. 문제를 처음 드러낸 commit 확인
4. 수정 과정의 중간 commit 확인
5. 최종 code/log/report 확인
6. 당시 발표자료나 문서와 교차 검증
7. 위 근거를 바탕으로 상황 → 문제 → 판단 → 조치 → 결과 복원

특히 commit message만으로 결론을 내리지 않고 diff를 확인합니다.

예:

- `fix done`이라는 이름보다 실제 diff에서 `weight.detach()` → `weight().int_repr()` 변경을 확인
- `refactoring for synth`라는 이름보다 실제 `reg + always` → `wire + generate + assign` 변경을 확인
- `sidecar`라는 표현보다 requirements에서 서로 다른 `transformers` 버전 충돌을 확인

이렇게 복원한 내용은 `experiences/` 상세 문서에 먼저 기록한 뒤 이력서/자소서에는 핵심만 압축합니다.

## 8. 실패와 미완료 결과 작성 원칙

실패한 프로젝트나 실험을 성공처럼 포장하지 않습니다.

좋은 서술:

- synthesis/P&R final stage까지 수행했지만 timing closure는 달성하지 못했다
- gate-level 비교 환경은 만들었지만 정상 waveform을 확보하지 못해 Netlist accuracy를 확인하지 못했다
- 무수수료 backtest는 수익이었지만 실제 수수료 적용 후 손실로 바뀌어 전략이 실용적이지 않음을 확인했다

이 경우 결과 뒤에 다음을 붙입니다.

- 어디까지 성공했는가
- 어디서 실패했는가
- 무엇을 확인했는가
- 다음에는 어떤 지표나 검증을 먼저 봐야 하는가

`실패했다`보다 **실패를 어떻게 확인했고 어떤 판단을 얻었는가**가 중요합니다.

## 9. 문항 분석 순서

자소서를 바로 쓰기 전에 문항을 다음처럼 해석합니다.

### 직무 준비 / 직무 역량

`무엇을 공부했다`보다 **실제로 무엇을 만들고 검증했는지**를 중심으로 씁니다.

구조 예시:

1. 지원 직무에서 중요하다고 보는 역량
2. 그 역량을 보여주는 대표 경험
3. 구체적인 문제와 본인의 역할
4. 기술적 판단 또는 개선 과정
5. 입사 후 연결점

### 어려웠던 일 / 문제 해결

어려웠다는 감정보다 **문제의 원인을 어떻게 좁혔는지**를 보여줍니다.

구조 예시:

1. 정상 상태와 문제 상태
2. 처음 세운 가설
3. 확인한 중간 결과 또는 실험
4. 원인 발견
5. 해결 또는 의사결정
6. 이후 달라진 방식

### 협업

`소통을 잘했다`고 결론부터 쓰지 않고, 서로 다른 역할 사이에서 **무엇을 맞췄는지**를 적습니다.

예:

- 개발자와 디자이너 사이의 리소스 형식
- 센서, 서비스, UI 사이의 데이터 규격
- 화면 요구사항과 DB 구조 사이의 연결

### 실패 / 아쉬운 결과

성공으로 억지로 바꾸지 않습니다. 실패했더라도 다음이 분명하면 좋은 소재가 됩니다.

- 무엇을 검증하려 했는가
- 어떤 지표로 실패를 확인했는가
- 왜 기대와 달랐는가
- 다음에는 무엇을 먼저 확인할 것인가

## 10. 경험 선택 기준

회사 이름에 맞춰 경험을 억지로 끼우기보다 **직무에서 실제로 필요한 행동과 가까운 경험**을 고릅니다.

### Software / Application

우선 후보:

- HummingBlocks
- Beamworks
- HCI Stock Service

강조점:

- 요구사항을 기능으로 바꾸는 과정
- 예외 처리
- 사용 흐름 개선
- 실제 출시와 운영

### Computer Vision / Imaging

우선 후보:

- HummingBlocks
- Computer Vision 수업 및 실습
- CNN Accelerator

강조점:

- 입력 환경 변화
- 모델 출력 후처리
- 정확도와 속도 비교
- 중간 결과를 확인하는 디버깅

### Embedded / HW-SW Integration

우선 후보:

- webOS Smart Planter
- Paperware
- Verilog CPU
- CNN Accelerator

강조점:

- 장치 사이의 데이터 흐름
- 하드웨어 제어
- 인터페이스 규격
- 파형 및 연산 결과 검증

### AI / Data

우선 후보:

- Crypto LOB Prediction
- HummingBlocks
- CNN Accelerator
- Mallo

강조점:

- 모델 자체보다 데이터, 평가 기준, 실제 활용 가능성까지 확인한 과정
- 모델 비교 결과를 제품의 latency/quality/deployment 기준과 연결한 의사결정

## 11. 작성 프로세스

1. 채용 공고에서 반복되는 역할과 기술을 표시합니다.
2. 문항이 실제로 묻는 행동을 한 문장으로 바꿉니다.
3. `experiences/`에서 가장 가까운 경험 1개를 우선 선택합니다.
4. 필요한 경우 보조 경험 1개만 추가합니다.
5. 경험의 근거가 부족하면 repository commit, log, 발표자료, Drive 원본을 먼저 확인합니다.
6. 상황 → 문제 → 판단 → 조치 → 결과 순서로 사실관계를 정리합니다.
7. 초안에서는 경험 설명 → 문제 → 행동/판단 → 결과 → 직무 연결 순서로 압축합니다.
8. 수치에는 baseline, sample 수, 측정 환경 등 필요한 맥락을 붙입니다.
9. 팀 성과, 개인 기여, 후속 제품 실적을 구분합니다.
10. 불필요한 추상어와 반복을 제거합니다.
11. 제한 글자 수에 맞게 확장하거나 압축합니다.
12. 마지막으로 source와 실제 기여를 다시 대조합니다.

## 12. 최종 체크리스트

- [ ] 문항에 직접 답하고 있는가?
- [ ] 첫 문단에서 핵심이 보이는가?
- [ ] 경험을 모르는 사람도 상황을 이해할 수 있는가?
- [ ] 팀 규모, 기간, 역할이 필요한 경우 명확한가?
- [ ] 팀 성과와 개인 기여가 구분되는가?
- [ ] 기존 baseline과 직접 구현 범위가 구분되는가?
- [ ] 문제 해결 과정에 판단 근거가 있는가?
- [ ] 비교 실험이라면 baseline, 후보, 지표, 최종 선택이 모두 있는가?
